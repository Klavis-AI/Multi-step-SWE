# PDF 1.6 and 1.7

Normative text: `/opt/pdfspec/ISO-32000-1-2008.txt` (ISO 32000-1:2008). Clause and table
numbers below are that document's. Where it describes a feature introduced after PDF 1.7,
that feature is not part of this milestone.

The previous milestones' clauses, in `/app/SPEC/pdf13.md`, `/app/SPEC/pdf14.md` and
`/app/SPEC/pdf15.md`, still apply in full. This document adds to them and replaces none of
them.

The header version is not a gate on which structures may appear. A file declaring 1.3,
1.4 or 1.5 that uses every structure below shall be read exactly as one declaring 1.7.
Two of the operations below — generating a field appearance and flattening annotations —
*write* a file; everything else in this document is reading.

## 1. Encryption — clause 7.6

### 1.1 General — 7.6.1, table 20

A document is encrypted when its trailer dictionary carries an `/Encrypt` entry; the
absence of that entry means the document is not encrypted, and nothing else may be taken
as evidence either way. Encryption applies to **all strings and streams** in the file,
with exactly these exceptions:

* the values of the trailer's `/ID` entry;
* any string inside the encryption dictionary itself;
* strings inside a stream that is itself encrypted — a content stream's or an object
  stream's contents are encrypted once, as the stream, and the strings within them are not
  encrypted again.

Integers, booleans, names and the file's structure are not encrypted, which is what allows
the cross-reference data to be followed before any key exists.

The entries common to all encryption dictionaries (table 20) that this milestone requires:

* `/Filter` — required, a name identifying the security handler. `/Standard` is the
  password-based handler every conforming reader shall support and is the only one in
  scope here.
* `/SubFilter` — optional, the syntax of the dictionary's contents, allowing a document to
  be decrypted by a handler other than the preferred one. Read and reported; nothing
  depends on it.
* `/V` — required, the algorithm selector, and with it the key length. `0` and `3` are
  undocumented or unpublished and are out of scope. **`1`** is 40-bit RC4 with `/Length`
  absent or 40. **`2`** is RC4 with the key length `/Length` gives, in bits, a multiple of
  8 between 40 and 128. **`4`** (PDF 1.5) means the handler uses crypt filters: the
  algorithm is no longer implied by `/V` and is named in `/CF` instead.
* `/Length` — optional, the key length in **bits**, default 40. Meaningful for `/V` 2 and
  above.
* `/CF` — required when `/V` is 4: a dictionary of crypt filter dictionaries by name (1.8
  below).
* `/StmF` — the name of the crypt filter for all streams; `/StrF` — the same for all
  strings. Both default to `/Identity`, meaning the data is passed through unchanged. Both
  are meaningful only when `/V` is 4 or greater.
* `/EFF` (PDF 1.6) — the crypt filter for embedded file streams that carry no specifier of
  their own. Read and reported; no case depends on it.

Strings in the encryption dictionary shall be direct objects, and the dictionary's own
contents are not encrypted. A reader that decrypts `/O` or `/U` before using them has
already failed.

### 1.2 The general encryption algorithm — 7.6.2, Algorithm 1

Two ciphers are in scope. **RC4** is a symmetric stream cipher and does not change the
length of the data. **AES** (PDF 1.6) is a symmetric block cipher used here in Cipher
Block Chaining mode with a 16-byte block; the 16-byte initialization vector is stored as
**the first 16 bytes of the encrypted stream or string**, and the plaintext is padded as
RFC 2898 (PKCS #5) describes: for an original length M the pad is `16 - (M mod 16)` bytes
each holding that same value, and a message whose length is a multiple of 16 still gets a
full 16 bytes of `0x10`. The pad is removed on decryption; a reader that leaves it in
place appends up to sixteen stray bytes to every content stream, which is not a decryption
failure the tools will report for you.

**Algorithm 1** derives the key for one object from the file key:

a) take the object and generation numbers from the identifier of the indirect object
   containing the string or stream — for a string inside an object, the containing
   object's identifier;
b) extend the *n*-byte file key by the low-order 3 bytes of the object number and the
   low-order 2 bytes of the generation number, low-order byte first (*n* is 5 unless `/V`
   is greater than 1, in which case it is `/Length` divided by 8). **If the cipher is
   AES, append four more bytes: `0x73 0x41 0x6C 0x54`;**
c) MD5 the result;
d) use the first `min(n + 5, 16)` bytes of that digest as the RC4 or AES key.

Stream data is encrypted **after** all stream encoding filters have been applied, so a
reader decrypts first and then decodes, and the `/Length` in the stream dictionary counts
the encrypted bytes. Strings are decrypted after escape-sequence processing and
hexadecimal decoding.

### 1.3 The standard security handler — 7.6.3.1

The handler admits up to two passwords, an owner password and a user password, and a set
of access permissions. A reader opening a document shall first attempt authentication with
the **empty user password**; if that succeeds the document opens with no prompt. If it
fails, either password shall open the document when supplied. Which one was supplied
determines what is permitted afterwards, and a conforming reader shall respect the
permissions even though nothing in the file enforces them.

A handler of revision 4 shall support crypt filters, limited to the `/Identity` filter and
to filters named `/StdCF` whose `/CFM` is `/V2` or `/AESV2` and whose `/AuthEvent` is
`/DocOpen`.

### 1.4 The standard encryption dictionary — 7.6.3.2, table 21

* `/R` — required. **2** when `/V` is less than 2 and no revision-3 permission is denied;
  **3** when `/V` is 2 or 3, or any revision-3 permission is denied; **4** when `/V` is 4.
* `/O` — required, a 32-byte string derived from both passwords (Algorithm 3).
* `/U` — required, a 32-byte string derived from the user password (Algorithm 4 or 5).
* `/P` — required, the permission flags (1.5).
* `/EncryptMetadata` — optional, boolean, default **true**, meaningful only when `/V` is 4 or greater.
  It changes the file key (Algorithm 2 step f), so a reader that ignores it decrypts
  nothing correctly in a document that carries `false`. It shall be read and reported.

### 1.5 Access permissions — table 22

`/P` is an integer interpreted as an **unsigned 32-bit** quantity; because the reserved
high bits are 1, it is written as a negative integer. Bits are numbered from 1 (low order).
A reader shall ignore every bit but 3, 4, 5, 6, 9, 10, 11 and 12:

| bit | meaning |
| --- | --- |
| 3 | print the document (at revision 3 or greater, possibly at reduced quality — see bit 12) |
| 4 | modify the contents by operations other than those of bits 6, 9 and 11 |
| 5 | copy or extract text and graphics (at revision 3 or greater, other than by bit 10) |
| 6 | add or modify text annotations and fill in form fields; with bit 4, create form fields |
| 9 | (revision 3+) fill in existing form fields even if bit 6 is clear |
| 10 | (revision 3+) extract text and graphics in support of accessibility |
| 11 | (revision 3+) assemble the document even if bit 4 is clear |
| 12 | (revision 3+) print to a faithful digital copy |

Which bits are meaningful, and how a reader words them, depends on `/R` as well as on
`/P`; a report derived from `/P` alone is wrong for a revision-2 document.

### 1.6 The file key — 7.6.3.3, Algorithm 2

From a password string: pad or truncate it to exactly 32 bytes using the padding string

```
28 BF 4E 5E 4E 75 8A 41 64 00 4E 56 FF FA 01 08
2E 2E 00 B6 D0 68 3E 80 2F 0C A9 FE 64 53 69 7A
```

(an empty password becomes the whole padding string); MD5 that; add the value of `/O`; add
`/P` as a 32-bit unsigned number, low-order byte first; add the **first element of the
trailer's `/ID` array**; then, at revision 4 or greater, if metadata is not being
encrypted, add four bytes of `0xFF`. Finish the hash. At revision 3 or greater, re-hash the
first *n* bytes of the digest 50 times. The key is the first *n* bytes of the final digest,
where *n* is 5 at revision 2 and `/Length` / 8 above it.

### 1.7 Password algorithms — 7.6.3.4, Algorithms 3 to 7

`/O` (Algorithm 3) is the padded user password encrypted with RC4 under a key derived from
the padded owner password — MD5, then 50 further MD5 rounds at revision 3 or greater, then
19 further RC4 rounds with the key XORed by the iteration counter. `/O` therefore depends
only on the two passwords and the revision, and **not on the cipher**: two documents
differing only in AES versus RC4 have byte-identical `/O`.

`/U` is the padded string encrypted under the file key at revision 2 (Algorithm 4); at
revision 3 or greater (Algorithm 5) it is MD5 of the padding string plus the first `/ID`
element, encrypted under the file key, put through 19 further XOR-keyed RC4 rounds, and
padded out to 32 bytes with arbitrary bytes — which is why **only the first 16 bytes of
`/U` are significant** at those revisions.

Authentication is Algorithm 6 for the user password — recompute `/U` and compare, on the
first 16 bytes at revision 3 or greater — and Algorithm 7 for the owner password: derive
the key from the supplied password as in Algorithm 3, decrypt `/O` (20 XOR-keyed rounds at
revision 3 or greater, counter 19 down to 0), and authenticate the result as a user
password. A document whose `/U` does not authenticate under the empty password and cannot
be opened with a supplied one shall fail, rather than return a partly decrypted document.

### 1.8 Crypt filters — 7.6.5, tables 25 and 26

When `/V` is 4, `/CF` maps names to crypt filter dictionaries and `/StmF` and `/StrF`
select which applies by default to streams and to strings. A crypt filter dictionary
carries:

* `/Type` — optional, `/CryptFilter` if present;
* `/CFM` — the method. **`/None`** (default) leaves decryption to the handler; **`/V2`**
  is RC4 under Algorithm 1; **`/AESV2`** (PDF 1.6) is AES-128 in CBC mode under Algorithm
  1, with the initialization vector in the first 16 bytes. Only these values are defined,
  and a file using another shall be reported as encrypted with an unsupported algorithm
  rather than silently mis-decrypted;
* `/AuthEvent` — `/DocOpen` (default) or `/EFOpen`; ignored, and treated as `/DocOpen`,
  for a filter named by `/StmF` or `/StrF`;
* `/Length` — the key length. Note the standard security handler expresses it **in bytes**
  here (16 meaning 128 bits) while `/Length` in the encryption dictionary is in bits.

`/Identity` (table 26) is the one standard name: data passes through untouched. A stream
may also name a crypt filter through the `Crypt` stream filter and its decode parameters
(7.4.10, table 14), whose `/Name` defaults to `/Identity`; this shall be read and reported.

### 1.9 Public-key security handlers — 7.6.4

`/Filter /Adobe.PubSec` and the entries of tables 23, 24 and 27 shall be read and reported
as written, and a document using them shall not be mistaken for an unencrypted one. **No
case requires decrypting such a document**; this milestone implements the standard
handler only.

## 2. The JBIG2Decode filter — clause 7.4.7, table 12

`JBIG2Decode` (PDF 1.4) decodes monochrome, 1-bit-per-pixel image data. It applies to
image XObjects and **shall not be used with inline images**. This milestone applies the
filter; the previous milestones' rule for an undecodable chain no longer covers it.

PDF carries JBIG2 in the *embedded file organization*, with these consequences, all
normative:

* the JBIG2 file header, the end-of-page segments and the end-of-file segment **shall not
  appear** in a PDF stream. A reader shall not require them, and shall not fail on a
  stream that omits them — the omission is the conforming case;
* the image XObject shall contain **all segments associated with the JBIG2 page that image
  represents**, with each segment's page association field set to 1;
* segments whose page association is 0 are *global* segments and shall be placed in a
  separate stream named by the filter's one decode parameter:

  | key | type | value |
  | --- | --- | --- |
  | `/JBIG2Globals` | stream | a stream holding the JBIG2 global (page 0) segments |

  That stream may be shared by several image XObjects. **The globals are load-bearing**: a
  page stream whose symbol dictionary lives in the globals cannot be decoded without them,
  and a reader that ignores `/DecodeParms` here produces no image rather than a wrong one.
  Where a filter chain has several stages, `/DecodeParms` is an array positionally
  matching `/Filter`, and the entry for the `JBIG2Decode` stage is the one that carries
  `/JBIG2Globals`.

The image dictionary shall agree with the decoded data: `/Width`, `/Height`,
`/BitsPerComponent` 1 and a 1-component colour space. Decoding a payload that is corrupt or
truncated shall not fail the document: the page still reads, other images on it are
unaffected, and the failure is reported as a diagnostic rather than as a non-zero status.
`/app/TEST_INTERFACE.md` §4.1 states precisely which properties of a JBIG2 image are
compared — the filter's occurrence and the codestream as stored — and which are not.

## 3. The JPXDecode filter — clause 7.4.9

`JPXDecode` (PDF 1.5) decodes JPEG2000 data. It applies only to image XObjects, never to
inline images. **The previous milestone carried such a stream through unchanged; this one
applies the filter.** The raw-byte and refusal obligations that milestone stated are
unchanged and still apply.

The filter expects a **full JPX file structure**, and both packagings shall be accepted:
the JP2 container and a bare codestream. Both carry, or imply, everything needed to
interpret the samples — dimensions, bit depth per component (any value from 1 to 38) and
colour space — so no decode parameters exist and none are needed.

The constraints the clause places on the image dictionary, all of which shall be honoured:

* `/Width` and `/Height` shall match the width and height in the JPEG2000 data;
* `/ColorSpace` is **optional**, because the data carries its own. When present it
  determines how the samples are interpreted **and the colour space in the data shall be
  ignored**; the channel count shall match the component count. Any space but `Pattern` may
  be used, and an `Indexed` space is limited to 256 colours;
* when `/ColorSpace` is absent, the data's own specification is used; where several are
  given, the one with the highest precedence and best approximation is preferred, and where
  none is supported the space is `DeviceGray`, `DeviceRGB` or `DeviceCMYK` according to
  whether the data has 1, 3 or 4 channels;
* `/SMaskInData` selects packaged opacity; when it is nonzero there shall be exactly one
  opacity channel and `/SMask` shall not be present;
* `/Decode` **shall be ignored** except where `/ImageMask` is true, in which case the data
  provides a single 1-bit channel.

Data in PDF is limited to the JPX baseline feature set, plus enumerated colour spaces 12
(CMYK) and 19 (CIEJab). Decoding is required to be **lossless where the codestream is
lossless**: the samples a JPEG2000 image yields shall equal the samples of the same image
stored uncompressed. **This property is NOT compared:** no case compares a decoded image
against an uncompressed twin. What `/app/TEST_INTERFACE.md` §4.1 compares for these
filters is the `pdfimages -list` row, the files `pdfimages -jbig2` writes out, and the
refusal of `--filtered-stream-data` at exit 2. A
payload that does not parse shall be reported and shall not fail the document.

## 4. Interactive forms — clause 12.7

### 4.1 General — 12.7.1

An interactive form — an AcroForm — is a document-wide collection of fields, each defined
by a field dictionary, organised hierarchically and inheriting attributes from ancestors. A
field with field children is *non-terminal*; one without is *terminal*. A terminal field's
children may be **widget annotations** that give it a position and an appearance, and where
there is exactly one such annotation **the field dictionary and the annotation dictionary
may be merged into a single dictionary** — the usual case, and one a reader shall handle.
Where such an object defines an appearance stream, the appearance shall be consistent with
the object's current value as a field. Interactive forms are unrelated to form XObjects
despite the name.

### 4.2 The interactive form dictionary — 12.7.2, table 218

The catalogue's `/AcroForm` entry:

* `/Fields` — required, an array of references to the root fields. An empty array is a
  document with no fields, and a catalogue with no `/AcroForm` is a document with no form
  at all;
* `/NeedAppearances` — optional, boolean, **default false**. It specifies whether the
  reader shall construct appearance streams and appearance dictionaries for the document's
  widget annotations. This one boolean decides, for a field whose stored appearance and
  whose value disagree, which of the two a reader shows — see 4.4;
* `/SigFlags` — optional (PDF 1.3), integer. Bit 1 `SignaturesExist` says the document
  contains at least one signature field; bit 2 `AppendOnly` says it contains signatures
  that a non-incremental save may invalidate (table 219). Read and reported;
* `/DR` — optional, the default resource dictionary used by field appearance streams. It
  shall contain at least a `/Font` entry, and it is where the font named by `/DA` is
  resolved;
* `/DA` and `/Q` — optional, document-wide defaults for the corresponding field entries;
* `/CO` — required when any field has a calculation action; an array giving calculation
  order. Read and reported, never executed;
* `/XFA` — optional (PDF 1.5), a stream or an array of string/stream pairs. It shall be
  read and reported as written and **shall not be interpreted**; the field dictionaries
  remain the definition of the form here.

### 4.3 Field dictionaries — 12.7.3.1, table 220

Every field dictionary is an indirect object. Inheritable entries are taken from the parent
where the field itself does not define them:

* `/FT` — required for terminal fields, inheritable: `/Btn`, `/Tx`, `/Ch` or `/Sig`
  (PDF 1.3). A non-terminal field may carry it purely to be inherited;
* `/Parent`, `/Kids` — the hierarchy. A field has at most one parent. In a terminal field
  `/Kids` holds widget annotations, and is **omitted when the single widget is merged into
  the field dictionary**;
* `/T` — the partial field name; the fully qualified name is the `/T` values from the root
  down, joined by periods (12.7.3.2). Two fields with the same fully qualified name are the
  same field and share a value;
* `/TU`, `/TM` — the alternate and mapping names. `/TU` is the text a reader uses when it
  must name the field;
* `/Ff` — inheritable field flags, default 0 (table 221; table 228 for text fields);
* `/V` — inheritable, **the field's value**, its type depending on `/FT`: a text string for
  `/Tx`, a name for a checkbox, a signature dictionary for `/Sig`;
* `/DV` — the default value, restored by a reset; `/AA` — additional actions, read and
  reported, never executed.

### 4.4 Variable text and appearances — 12.7.3.3 (table 222), 12.5.5 (table 168)

Where a field's contents are not known in advance, the document cannot supply a static
appearance and **the reader shall construct one**, combining the field's text with:

* `/DA` — required, inheritable: a default appearance string holding graphics and text
  state operators that fix the size, font and colour of the field's text. The font it names
  is resolved in `/DR`;
* `/Q` — optional, inheritable: 0 left, 1 centred, 2 right, default 0;
* `/DS`, `/RV` — optional (PDF 1.5), the default style string and rich text value. Read and
  reported; the plain `/V` remains the value this milestone shows.

The constructed stream becomes the **normal appearance** `/N` in the appearance dictionary
of the field's widget annotation, and where the annotation has no appearance dictionary the
reader creates one. An appearance dictionary (table 168) holds `/N` (required), `/R` and
`/D`; each may be a stream or a subdictionary of states selected by the annotation's `/AS`.
Only `/N` matters here.

Two rules follow, and they are what this milestone measures:

* a field with a value and **no** appearance stream shall still show its value: the
  appearance is constructed from `/V`, `/DA` and `/DR`. A reader that shows nothing because
  `/AP` is absent is wrong;
* a field with a value and a **stale** appearance stream — one drawing something other than
  the current `/V` — shows the stored appearance when `/NeedAppearances` is absent or false,
  and the value when it is true. The flag is the whole of the difference; nothing else in
  the two documents need differ.

### 4.5 Text fields — 12.7.4.3, tables 228 and 229

A text field has `/FT /Tx` and a value that is a text string (or a stream, for a large
one). `/MaxLen` (table 229) is the maximum length in characters. Of the flags in table 228,
`Multiline` (bit 13), `Password` (bit 14), `FileSelect` (bit 21), `DoNotSpellCheck` (22),
`DoNotScroll` (23), `Comb` (25) and `RichText` (26) shall be read and reported; a password
field's value shall not be shown. Button (12.7.4.2) and choice (12.7.4.4) fields shall be
read and reported by the same rules; the value a choice field shows is `/V`, and a
checkbox's is the `/AS`-selected appearance state.

### 4.6 Widget annotations — 12.5.6.19, tables 164 and 165

A widget annotation is `/Subtype /Widget` with `/Rect` giving its position and `/F` the
annotation flags. Of those flags two decide whether the field is shown at all: **bit 2
`Hidden`** — do not display or print the annotation, regardless of its type or appearance
— and bit 6 `NoView`. A hidden widget contributes nothing, and its appearance stream, if
any, is not used. `/MK`, `/H`, `/A` and `/AA` shall be read and reported.

### 4.7 Flattening

Flattening is not an operation ISO 32000-1 defines; it is defined here, in the standard's
terms, because this milestone performs it. To flatten a page's annotations is to produce a
document in which, for each annotation being flattened:

* its effective appearance stream — the `/N` appearance, after `/NeedAppearances` has been
  honoured, in the state `/AS` selects — is drawn into the **page's own content stream**,
  transformed from the appearance's `/BBox` and `/Matrix` onto the annotation's `/Rect` by
  the algorithm of 12.5.5: the transformed bounding box is mapped corner to corner onto the
  rectangle;
* the annotation is then removed from the page's `/Annots` array, and the array itself is
  removed when it becomes empty;
* when no field is left anywhere, the catalogue's `/AcroForm` no longer describes a form,
  and a reader shall report the document as having none.

Three properties of the result are normative. The page's text content after flattening
**includes the field's value**, because the value is now drawn by the page. Flattening is
selective: `all`, the printable annotations only, or the screen ones only, in the sense of
the `Print` flag of table 165. And flattening a field whose appearance is not trustworthy —
a value with no appearance stream, in a document that does not set `/NeedAppearances` —
**discards the value**, because there is no appearance to draw and the field is gone
afterwards. That is the correct outcome of an incorrect document, and
`/app/TEST_INTERFACE.md` §4.1 expects it as it stands.

## 5. Digital signatures — clause 12.8

### 5.1 General — 12.8.1

A signature (PDF 1.3) stores information about a signer and about the state of the document
when it was signed. Signature information lives in a **signature dictionary** (table 252),
which is the value `/V` of a signature field. A byte range digest is computed over the
range of bytes the dictionary's `/ByteRange` describes; that range should be the entire file
**excluding the signature value itself**, which is why `/ByteRange` holds more than one
pair. When a byte range digest is present, **every value in the signature dictionary shall
be a direct object**.

A document may carry approval signatures, at most one certification signature (PDF 1.5) —
whose dictionary carries a signature reference dictionary with a `DocMDP` transform method
and may be named by the permissions dictionary's `/DocMDP` — and at most two usage rights
signatures. All three shall be read and reported; the distinction is structural here.

### 5.2 The signature dictionary — table 252

* `/Type` — optional, `/Sig` if present;
* `/Filter` — required, the preferred signature handler, e.g. `/Adobe.PPKLite`;
* `/SubFilter` — optional, the encoding of the signature value: `adbe.x509.rsa_sha1`,
  `adbe.pkcs7.detached` or `adbe.pkcs7.sha1` (PDF 1.6), or a name a developer registered.
  **A name this implementation does not recognise is not an error**: it shall be read and
  reported as written;
* `/Contents` — the signature value, a hexadecimal string between `<` and `>` that fits
  exactly in the gap `/ByteRange` leaves and is padded with zeros to fill it. It shall be
  read and reported as the string it is, and **its contents shall not be interpreted**;
* `/ByteRange` — required for a signature in a signature field: an array of pairs, each a
  starting offset and a length in bytes. It shall be reported **as written**. A
  `/ByteRange` that does not describe the file is a malformed document, not a reason to
  refuse to report it;
* `/Reference` — optional (PDF 1.5), an array of signature reference dictionaries (5.4);
  `/Changes` — optional, three integers;
* `/Name`, `/M`, `/Location`, `/Reason`, `/ContactInfo` — optional, the signer's name, the
  time of signing, and prose. `/M` is a date string in the usual form;
* `/R`, `/V`, `/Prop_Build`, `/Prop_AuthTime`, `/Prop_AuthType` — read and reported.

A signature dictionary is reached only through the field that holds it, and it is a
dictionary like any other: `/app/SPEC/pdf13.md`'s rules for objects and strings apply to it
unchanged.

### 5.3 Signature fields — 12.7.4.5, tables 232 and 219

A signature field is a form field with `/FT /Sig`. Its `/V`, when present, is a signature
dictionary; **when `/V` is absent the field exists and is not signed**, and that is a state
a reader shall report rather than treat as an error or as a missing field. `/Lock` and `/SV`
(table 232) shall be read and reported. A signature field is described by a widget
annotation like any other field; a field intended to be invisible has a `/Rect` of zero
width and height, and shall also be treated as invisible when the `Hidden` or `NoView` flag
is set.

### 5.4 Transform methods — 12.8.2

A signature reference dictionary (table 253) carries `/TransformMethod` — `DocMDP`, `UR` or
`FieldMDP` — with `/TransformParams` (tables 254 to 256), `/Data`, and `/DigestMethod`
(`MD5` or `SHA1`). For `DocMDP`, `/P` states which changes invalidate the signature: 1 the
document is final, 2 and 3 permit form-filling and commenting workflows. **All of this shall
be read and reported and none of it shall be enforced.** No permission in a transform
parameters dictionary restricts anything this implementation does, and no case
depends on one.

### 5.5 Interoperability — 12.8.3, table 257

`adbe.pkcs7.detached` is the recommended encoding and carries a detached PKCS#7 object over
the byte range; `adbe.pkcs7.sha1` carries a PKCS#7 over a SHA-1 digest; `adbe.x509.rsa_sha1`
carries a PKCS#1 object. The digests each supports are SHA1 (1.3), SHA256 (1.6), SHA384,
SHA512 and RIPEMD160 (1.7). This is recorded so that a `/SubFilter` name can be reported in
context. **None of these formats is parsed by this milestone.**

### 5.6 What is not required

Verification is not part of this milestone, and no case asks for it. Specifically:
no digest is computed over any byte range; `/Contents` is never parsed as a cryptographic
object; no certificate, certificate store, revocation list or timestamp is consulted; and
`/ByteRange` is never checked against the file it describes. A reader that reports a
malformed signature's structure faithfully is correct; one that refuses to report it, or
that claims a verdict about it, is not.

## 6. What the utilities must report

The interfaces, their option spellings and the comparison rules are in
`/app/TEST_INTERFACE.md`.

* `pdfinfo` — the fields of the previous milestones, with `Encrypted` now carrying the
  cipher and the permissions of the document it opened, and `Form` reporting whether the
  document has an interactive form.
* `pdftotext` — the text of the requested pages of a document it has decrypted, including
  the value of a filled field as the constructed or stored appearance draws it.
* `pdffonts` — the fonts of a decrypted document, the default resource font of a
  constructed appearance included where that appearance is part of the page.
* `pdfimages -list` — one row per image, naming the filter that was recognised, without
  decoding anything; `pdfimages -jbig2` — the stored codestream of a `JBIG2Decode` image,
  byte for byte, with its globals in their own file. Decoded pixels are not compared for
  either codec.
* `pdfsig` — for each signature field: its name, its `/SubFilter`, its `/ByteRange`, and
  whether it is signed at all; and the fact that a document carries no signature.
* `qpdf --show-encryption` — `/R`, `/P`, the permissions they imply, and, for `/V` 4 or
  greater, the
  method used for streams, strings and the file; `--is-encrypted` — whether the document is
  encrypted, without a password; `--decrypt` — the same document with no encryption on it.
* `qpdf --show-object=N` — one object of a decrypted document, the encryption dictionary
  included; `--filtered-stream-data` — a stream's decoded, decrypted bytes, or a refusal
  where the chain names a codec this option does not apply.
* `qpdf --generate-appearances`, `--flatten-annotations` — a document whose field
  appearances are current, and one whose annotations have become page content.
