# Milestone 07 — tree-sitter 0.25.0

This release raises the parser ABI to **15** and spends the extra room on three
things the generated parser could not previously carry: its own name and
version, the supertype relation, and a set of **reserved words**. Two of those
become observable through the grammar language and the query language, so this
milestone changes all three layers at once.

Seven changes, each with its own section:

1. generated parsers declare ABI **15**, and a repository opts into it by
   carrying a `tree-sitter.json`;
2. the grammar gains a `reserved` option and a `reserved(…)` combinator;
3. queries gain the `(supertype/subtype)` pattern, and it is **verified**
   against the grammar at query-compile time;
4. queries can match `MISSING` nodes;
5. `test` can select corpus files by name;
6. `parse` can print a **concrete** syntax tree;
7. `generate` can write its output somewhere other than `src/`.

Everything the foundation documents and earlier milestones added still holds
except where a section below says otherwise, and each one says so explicitly.

---

## 1. ABI 15

### 1.1 `tree-sitter.json` selects it

Milestone 03 raised the default ABI from 13 to 14. The newest ABI this release
emits is **15**, but unlike the previous raise it is not simply the new
default: a repository gets it only when it declares itself with a
`tree-sitter.json` (milestone 06 §3.1).

`generate` looks for `tree-sitter.json` — the file milestone 06 §3.1 describes
— in the directory it is generating in and, failing that, in each **ancestor**
directory in turn, stopping at the first one that has it. It is the file's
presence that selects the ABI.

When one is found, `generate` writes

```c
#define LANGUAGE_VERSION 15
```

into `src/parser.c` and emits the ABI 15 tables of §1.4.

Because the lookup walks ancestors, a repository nested inside another
repository that has a `tree-sitter.json` is generated at ABI 15 as well. Keep
unrelated fixtures side by side rather than nested if you need one of each.

### 1.2 Without it: ABI 14, a warning on stdout, and no migration

When no `tree-sitter.json` is found in the directory or any ancestor,
`generate` **succeeds** — exit 0, the usual files, a parser that loads and
parses — and emits ABI 14:

```c
#define LANGUAGE_VERSION 14
```

It reports the fallback on **stdout**, naming `tree-sitter.json` and the ABI it
used instead. The wording is not an interface; that the run succeeds and that
the parser declares 14 is.

**This overturns milestone 06 §3.2.** In a repository whose `package.json`
carries a `"tree-sitter"` key and which has no `tree-sitter.json`, `generate`
no longer migrates the configuration. It writes no `tree-sitter.json`, and it
leaves `package.json` exactly as it found it — the `"tree-sitter"` key is still
there afterwards. A repository in that state stays in it: every later
`generate` takes the same fallback and emits ABI 14 again. Milestone 06 §3.1
(the shape of the file), §3.3 (`generate` writes only `src/` and
`tree-sitter.json`, adds no `"main"` key and creates no `package.json`) and
§3.4 (a `tree-sitter.json` and no `package.json` is a complete repository) are
unaffected.

### 1.3 `--abi 14` and `--abi 15`

Milestone 02 §6.1 gives `generate --abi <version>` and its table of accepted
values. Two rows change:

| value | declared version |
| --- | --- |
| `14` | 14 |
| `15` | 15 |
| `latest` | 15 — the newest this release emits |

`--abi 15` produces an ABI 15 parser and `--abi 14` an ABI 14 one, in the same
repository, whatever §1.1 would have chosen on its own. Both exit 0 and write
the usual file set. The ABI is what selects the tables: an ABI 14 parser
generated by this release carries exactly what milestone 03 §2 requires of one
and none of §1.4's additions.

### 1.4 What an ABI 15 `src/parser.c` carries

Beyond everything ABI 14 already required, an ABI 15 parser defines the
supertype and reserved-word tables and wires them into the language struct:

| what | how it appears in `src/parser.c` |
| --- | --- |
| the number of supertypes | `#define SUPERTYPE_COUNT <n>` |
| the supertype symbols | a field initialiser written `.supertype_symbols =` |
| which subtypes each supertype has | a field initialiser written `.supertype_map_slices =` |
| the reserved-word table | a field initialiser written `.reserved_words =` |
| the grammar's name | a field initialiser written `.name =` |
| the grammar's version | a field initialiser written `.metadata =` |

`SUPERTYPE_COUNT` is defined in **every** parser this release generates,
including an ABI 14 one, where its value is `0`. The five field initialisers
appear only at ABI 15. `<n>` is the number of rules the grammar's `supertypes`
option lists (`10-grammar-dsl.md` §7.5).

The tables' element types, lengths and contents are not compared — that each is
defined and wired into the language struct is, exactly as milestone 03 §2 put
it for `ts_primary_state_ids`. `.name` and `.metadata` (`major_version`,
`minor_version`, `patch_version`) are filled in from the grammar's own `name`
in `grammar.js` and from `tree-sitter.json`'s `metadata.version` — a name in
the `tree-sitter.json` grammar entry does not override the one the grammar
declares. On the §1.1 route both inputs are to hand: the same
`tree-sitter.json` whose presence selects ABI 15 is one the binary refuses to
read without a `metadata.version`, so a run that reaches ABI 15 by that route
has already passed one through. The route is not the only one — §1.3's `--abi`
flag is another way to ask for ABI 15 — and a repository that reaches ABI 15
without a `tree-sitter.json` has no `metadata.version` to read at all; nothing
here requires one. The file carries the version as a string and the struct as
three numbers; how it splits one into the other is not fixed by this document
beyond that the string must be a three-part version — a file whose
`metadata.version` is not is a hard error rather than a parser that falls back.

Everything else about `generate`'s output is unchanged.

## 2. Reserved words

A **reserved word** is a token that is excluded from a position where it would
otherwise be accepted, so that a keyword cannot be mistaken for an identifier.
The grammar names the words; the generator excludes them.

### 2.1 The `reserved` grammar option

`grammar()` takes an eighth optional top-level setting beside the seven of
`00-overview.md`. `reserved` is an **object**, not an array: each key names a
*reserved-word set*, and each value is a function of `$` returning the list of
tokens in that set. The set named `global` is special — it applies everywhere
the grammar does not say otherwise.

```js
reserved: {
  global: $ => ['if'],
  key:    $ => ['let'],
},
```

Every element of a set must be a **token**: it must denote a single terminal —
a string literal, a regex or `token(...)` expression, or a reference to a rule
whose body is itself one of those. An element that would be more than one
token is not one: a `seq` of literals is a hidden rule with two children, so a
set naming `seq('a', 'b')` is rejected. A set naming something that is not a
token is rejected in the ordinary way of `10-grammar-dsl.md` §9.

Exclusion is applied through the grammar's keyword-extraction token, so a
grammar that uses `reserved` declares `word` (`10-grammar-dsl.md` §5.4). With
`global: $ => ['if']` and `word: $ => $.identifier`, the input

```text
let a = if;
```

no longer parses as a binding of `a` to an identifier named `if`: `if` is not
available as an `identifier` there, recovery takes over, and the tree is

```text
(source_file [0, 0] - [1, 0]
  (ERROR [0, 0] - [0, 11]
    (identifier [0, 4] - [0, 5])))
```

The rejection has a second shape, in the position where the grammar wants a
**word** rather than a value. `let if = b;` is the mirror image of the example
above, and the reserved word there is not merely dropped out of the recovery's
way — the recovering parser wraps it, together with the `=` it also cannot
place, in an `ERROR` node of its own:

```text
(source_file [0, 0] - [1, 0]
  (ERROR [0, 0] - [0, 11]
    (ERROR [0, 4] - [0, 8])
    (identifier [0, 9] - [0, 10])))
```

The nested `ERROR` spans `if` and the `=` that follows it, `[0, 4]` to
`[0, 8]`; the `let` and the `;` are anonymous and do not print; and the value
`b` is still read as an `identifier`. This nested node is not the
character-level one of `60-runtime.md` §2 — `if` *is* a token of the grammar,
so nothing here was lexed character by character — and it is therefore not
rewritten by the corpus rendering (`30-tree-output.md` §5) as `(UNEXPECTED …)`.
The same tree in that rendering is

```text
(source_file
  (ERROR
    (ERROR)
    (identifier)))
```

A word the grammar does **not** reserve is unaffected — with only `if`
reserved, `let let = b;` is still an ordinary `let_statement` with two
identifiers — and a reserved word is still perfectly usable wherever the
grammar mentions it as a literal, which is what makes `if (a) { b; }` keep
parsing.

### 2.2 `reserved(set, rule)`

Inside a rule body, `reserved(<set-name>, <rule>)` parses `<rule>` with the
named set in force instead of `global`:

```js
pair: $ => seq(reserved('key', $.identifier), ':', $.identifier, ','),
```

Within that `identifier` the `key` set applies and `global` does not. So in a
grammar reserving `if` globally and `let` in `key`:

| input | outcome |
| --- | --- |
| `let a = { if: b, };` | parses — `if` is a legal key, because `global` is not in force there |
| `let a = { let: b, };` | the key position rejects `let`; recovery produces an `ERROR` inside the object, replacing the `pair` and spanning `let: b,` — the tree is printed below |
| `let a = if;` | rejected as in §2.1 — an ordinary position, so `global` applies |

The switch is lexical and total: the named set replaces `global` for the
extent of the wrapped rule rather than adding to it.

The second row's tree, verbatim:

```text
(source_file [0, 0] - [1, 0]
  (statement [0, 0] - [0, 20]
    (let_statement [0, 0] - [0, 20]
      (identifier [0, 4] - [0, 5])
      (object [0, 8] - [0, 19]
        (ERROR [0, 10] - [0, 17]
          (identifier [0, 15] - [0, 16]))))))
```

The `if` in the first row is not merely accepted — it is a live key, so the
`pair` survives intact:
`(object (pair (identifier) (identifier)))`. Only the `key` set is replaced
inside the wrapped rule; `global` comes back the moment the rule ends, which is
why the third row still rejects `if`.

### 2.3 `reserved` in `src/grammar.json`

`10-grammar-dsl.md` §10 fixes the top-level keys of the grammar JSON. A tenth
key, `reserved`, is added after `supertypes`. It is an object mapping each set
name to an array of **rule objects**, in the §10 encoding, so the grammar above
normalises to

```json
"reserved": { "global": [ { "type": "STRING", "value": "if" } ] }
```

The key is written whenever the grammar sets `reserved`, at either ABI — it
records what the grammar meant, and §2.4 is about what the parser does with it.

### 2.4 Reserved words take effect only at ABI 15

The reserved-word table is an ABI 15 table (§1.4). A grammar using `reserved`
generates cleanly at ABI 14 and its `src/grammar.json` still carries the key,
but the resulting parser does not enforce anything: `let a = if;` parses as an
ordinary binding, exactly as it would in a grammar with no `reserved` at all.
This is the one place where the ABI a repository ends up at is visible in a
parse tree rather than in an artefact.

## 3. Supertype patterns in queries

### 3.1 `(supertype/subtype)`

`50-queries.md` §1.1 gives the node patterns. One more is added:

```text
(_statement/let_statement) @s
```

A pattern `(<supertype>/<subtype>)` matches a node of type `<subtype>` in a
position where the grammar derives it **through** `<supertype>`. It is written
with a `/` between the two names, inside one pair of parentheses, and it is a
node pattern like any other: it takes captures, fields, children and
quantifiers in the ordinary way, and it captures the *subtype* node — its
extent and its text are the subtype's.

The supertype is a hidden rule and so appears in no tree
(`10-grammar-dsl.md` §7.5). The pattern is how a query reaches that relation
without the node being there, which is what `supertypes` is for: `(_statement/…)`
says "in statement position" without the query having to know which concrete
statements exist.

### 3.2 The pair is verified when the query is compiled

Both halves are checked against the grammar, and a pair the grammar does not
have is a **compile error** — exit 1, no captures, a diagnostic whose wording
is not an interface, in the manner of `50-queries.md` §1.10:

| pattern | why it is rejected |
| --- | --- |
| `(_statement/identifier)` | `identifier` is not one of `_statement`'s alternatives |
| `(block/identifier)` | `block` is a node type, but not a **declared supertype** |

The first is the same kind of error as a structurally impossible pattern; the
second is new, and it is the stricter half: the left-hand name must appear in
the grammar's `supertypes` option, not merely exist. A query file that compiles
runs normally and one that does not runs not at all — there is no partial
compilation.

### 3.3 Verification needs an ABI 15 parser

The supertype relation reaches the query engine through the parser's supertype
tables, so only a parser generated at ABI 15 can be verified against. Compiled
against an **ABI 14** parser, `(supertype/subtype)` is accepted whatever the
two names are, the query exits 0, and it matches nothing. The same query file
and the same grammar therefore behave differently according to §1.1, and that
is the intended consequence rather than an accident: verification is a property
of the parser, not of the query file.

## 4. `MISSING` is queryable

`00-overview.md` defines a `MISSING` node as the zero-width node error recovery
inserts for a token the grammar required, and `30-tree-output.md` §5.1 gives
how one is printed. This release lets a query match one. Three patterns, all
new:

| pattern | matches |
| --- | --- |
| `(MISSING)` | any missing node |
| `(MISSING ";")` | a missing **anonymous** token whose type is `;` |
| `(MISSING identifier)` | a missing **named** node whose type is `identifier` |

The type is written exactly as `30-tree-output.md` §5.1 writes it in a tree: an
anonymous token's type is double-quoted, because the type is the literal's own
text, and a named type is written bare. A pattern naming a type the grammar has
but that is never missing in the input compiles and matches nothing — that is
an empty result, not an error.

A matched missing node is zero-width, so a capture of one reports `start` and
`end` at the same point and its text field is empty. Against the grammar of §2
and the input `let a = b` — which is missing its `;` — the pattern
`(MISSING ";") @m` prints, in the format milestone 02 §1.1 fixed:

```text
in.rez
  pattern: 0
    capture: 0 - m, start: (0, 9), end: (0, 9), text: ``
```

`(MISSING) @m` prints the same for that input, and matches the missing `}` of
an unclosed block just as readily. These patterns are a query-engine feature
and do not depend on the ABI.

## 5. `test --file-name <name>`

`tree-sitter test` gains an option that selects **corpus files** rather than
tests:

```text
tree-sitter test --file-name <name>
```

Only corpus files whose file name is exactly `<name>` are read; every other
file in the corpus directory is skipped, and the tests it holds are neither run
nor printed. Matching is on the **base name including its extension** and is
exact, not a substring and not a pattern: `--file-name basic.txt` selects
`test/corpus/basic.txt`, and `--file-name basic` selects nothing. The corpus
directory is searched to any depth as `40-corpus-tests.md` §1 already says, and
the name is matched against the file's own name wherever it was found, not
against its path.

A `<name>` that matches no file is not an error. No test runs, nothing is
reported as passing or failing, and the exit status is **0** — the same rule
`40-corpus-tests.md` §3 gives for a filter that selects nothing. Everything
else about a `test` run is unchanged, including which names are reported as
passed and failed, and the option composes with `--include` and `--exclude`
(milestone 04 §3) rather than replacing them.

## 6. `parse --cst`

```text
tree-sitter parse --cst [paths]...
```

prints a **concrete** syntax tree instead of the S-expression of
`30-tree-output.md` §1. The difference that matters is in the name: this
rendering prints **anonymous** nodes, which neither S-expression rendering
does. Exit status, language selection and everything else about `parse` are
unaffected; only what is printed changes.

For a parse that produced no error the block is the whole of stdout — there is
no trailing summary line after it.

### 6.1 The structure of a line

Each visible node occupies one line, parents before children, in source order.
A line is a range prefix, then indentation, then the node:

```text
<start_row>:<start_col><pad>- <end_row>:<end_col><pad><indent><node>
```

* rows and columns are zero-based and columns count bytes, as everywhere else
  (`00-overview.md`, `30-tree-output.md` §2). The end position is exclusive;
* `<indent>` is two spaces per level of depth, and the **root is already at one
  level**, so the root's kind is preceded by two spaces of indent and each
  further level adds two;
* both `<pad>` runs align the prefixes into columns. Let

      w(n) = floor(log10(n)) for n >= 1, and 0 for n = 0

  and let `W` be the largest value of `w(row) + w(len) + 1` over the rows of the
  input, where `len` is that row's length in bytes and `row` its zero-based
  index. Each `<pad>` is `max(1, W - w(row) - w(col))` spaces, computed from the
  row and column it follows. So both pad runs are at least one space, and a
  short position is padded more than a long one;
* `<node>` is, for a named node, its **field prefix** (§6.1.1) then its **error
  marker** (§6.1.2) then its kind, followed by a space and then — only if the
  node has no children — its source text in **backticks**. For an anonymous
  node it is the node's text in **double quotes**, with no field prefix, no
  error marker and no trailing space. For an anonymous node that is
  `MISSING` — a token the parser inserted, `60-runtime.md` §5 — it is
  `MISSING: ` followed by the node's kind in double quotes, again with no
  trailing space;
* `<indent>` is followed by **one further space** when the node is inside an
  error and does not itself have one. §6.1.3 gives the exact rule.

A named node *with* children therefore ends its line with the separating space
and nothing after it. That space is written; it is the same separator that a
leaf's backticked text follows. It is not stripped by the renderer, so an
implementation that omits it does not produce the same bytes.

### 6.1.1 The field prefix

If the node is named **and** occupies a child position that the grammar gave a
field name (`10-grammar-dsl.md` `field(name, rule)`), its kind is preceded by
that field name, a colon and one space — `name: identifier` — exactly as in the
S-expression rendering of `30-tree-output.md` §1. A child with no field has no
prefix. Anonymous nodes never carry one, even in a fielded position.

### 6.1.2 The error marker

If the node is named **and** it is an `ERROR`, or it has an `ERROR` or a
`MISSING` node anywhere beneath it, the character `•` (U+2022) is written
immediately before its kind — after the field prefix, if there is one. So the
marker travels up the spine from the offending node to the root: on a tree with
any error at all the root carries it.

A node with no error beneath it carries no marker, and an anonymous node never
carries one whatever is beneath it — an anonymous node has nothing beneath it.

The marker is a character in the line, not a colour: it occupies a column and
shifts the kind one place right relative to the same line in an error-free
tree.

### 6.1.3 The alignment space inside an error

Because the marker shifts a line right by one, the renderer puts an extra space
on the *unmarked* lines around it so that a region of the tree that is inside
an error stays aligned with itself. The rule is a flag the walk carries, and it
is stated here exactly because it is a column position:

* the flag starts **off** at the root;
* whenever the walk descends from a node to its **first child**, and that first
  child has an error beneath it or is one, the flag goes **on**;
* whenever the walk finishes a node's children and returns to its parent, and
  that parent does **not** have an error, the flag goes **off**;
* while the flag is on, a node that does *not* itself have an error is written
  with **one extra space** between its `<indent>` and its `<node>`. A node that
  does have an error gets no extra space — its `•` occupies that column
  instead.

Two consequences are worth stating, because they are what makes the rule
observable. First, the flag turns on only through a **first** child: a tree
whose first statement parses cleanly and whose second is an `ERROR` never turns
it on, so no line in that tree carries the extra space even though the root is
marked. Second, once on, the flag stays on through the whole subtree it entered
— it is not re-tested at each level on the way down.

### 6.2 Two worked examples

Both are against the grammar of §2. For `let a = b;` followed by a newline —
`W` is 2 here, so `0:0` is followed by two spaces and `0:10` by one:

```text
0:0  - 1:0    source_file
0:0  - 0:10     let_statement
0:0  - 0:3        "let"
0:4  - 0:5        identifier `a`
0:6  - 0:7        "="
0:8  - 0:9        identifier `b`
0:9  - 0:10       ";"
```

The `"let"`, `"="` and `";"` lines have no counterpart in either S-expression
rendering. For `if (a) { b; }` followed by a newline:

```text
0:0  - 1:0    source_file
0:0  - 0:13     if_statement
0:0  - 0:2        "if"
0:3  - 0:4        "("
0:4  - 0:5        identifier `a`
0:5  - 0:6        ")"
0:7  - 0:13       block
0:7  - 0:8          "{"
0:9  - 0:11         expression_statement
0:9  - 0:10           identifier `b`
0:10 - 0:11           ";"
0:12 - 0:13         "}"
```

Note that `_statement` is hidden and so contributes no line, exactly as it
contributes no node to an S-expression: this rendering prints the tree's
anonymous nodes, not its hidden ones. Neither tree has an error, so no line in
either carries a marker or an extra space.

### 6.3 A third example — fields, a marker and the alignment space

The grammar of §2 has no fields, so this example uses a second one:

```js
module.exports = grammar({
  name: 'rezfld',
  extras: $ => [/\s/],
  rules: {
    source_file: $ => repeat($._statement),
    _statement: $ => choice($.let_statement, $.expression_statement),
    let_statement: $ => seq(
      'let', field('name', $.identifier), '=', field('value', $.number), ';'),
    expression_statement: $ => seq($.identifier, ';'),
    identifier: $ => /[a-z_]+/,
    number: $ => /[0-9]+/,
  },
});
```

For `let a = 1` followed by a newline — a `;` is missing, so the parser inserts
one and `parse` exits 1. The one row is 9 bytes long, so `W` is 1 and every pad
is one space:

```text
0:0 - 1:0   •source_file
0:0 - 0:9     •let_statement
0:0 - 0:3        "let"
0:4 - 0:5        name: identifier `a`
0:6 - 0:7        "="
0:8 - 0:9        value: number `1`
0:9 - 0:9       MISSING: ";"
```

Everything §6.1 adds is visible here. `source_file` and `let_statement` carry
`•` because the inserted `;` is beneath them. `identifier` and `number` carry
their field prefixes. The inserted token is anonymous, so it carries neither a
prefix nor a marker, and renders as `MISSING: ";"`. And the flag of §6.1.3 is
on — `source_file`'s first child is the marked `let_statement` — so the four
unmarked lines under `let_statement` each carry one extra space, which is why
`"let"` sits one column right of where §6.2's `"let"` sits at the same depth,
while `MISSING: ";"` does not, having an error of its own.

Contrast `let a = 1;` and `let b = 2` on two lines. The root is still marked,
but its **first** child parses cleanly, so the flag never turns on and no line
carries the extra space; `W` is 2, from the first row's ten bytes:

```text
0:0  - 2:0    •source_file
0:0  - 0:10     let_statement
0:0  - 0:3        "let"
0:4  - 0:5        name: identifier `a`
0:6  - 0:7        "="
0:8  - 0:9        value: number `1`
0:9  - 0:10       ";"
1:0  - 1:9      •let_statement
1:0  - 1:3        "let"
1:4  - 1:5        name: identifier `b`
1:6  - 1:7        "="
1:8  - 1:9        value: number `2`
1:9  - 1:9        MISSING: ";"
```

(The blocks above are shown with trailing whitespace removed, as every captured
output in this task is; the renderer writes the separating space after
`source_file`, `let_statement` and every other kind.)

## 7. `generate -o <dir>`

```text
tree-sitter generate -o <dir>
tree-sitter generate --output <dir>
```

Writes the generated parser into `<dir>` instead of into `src/`. `<dir>` is
relative to the current directory, is created if it does not exist, and may
name a path several levels deep, in which case every level is created.

The files go **directly** into `<dir>` — the option replaces the `src/`
directory rather than relocating it, so `<dir>/src/` is not created:

| path | written |
| --- | --- |
| `<dir>/parser.c` | always |
| `<dir>/node-types.json` | always |
| `<dir>/grammar.json` | always |
| `<dir>/tree_sitter/parser.h` | always |

`src/` is not written at all: after `generate -o out` there is no
`src/parser.c`. The run is an ordinary successful `generate` in every other
respect — exit 0, the ABI chosen as §1.1 and §1.3 say, and the same contents it
would have written under `src/`.

> A parser written somewhere other than `src/` is not where `20-cli.md` §6.4
> looks for sources, so a repository generated this way cannot be loaded from
> its own directory until the files are in `src/`. That is the point of the
> option: it is for generating into a build directory, not for replacing the
> normal layout.
