# Documentation. No code reads this file.
#
# The alert pins this verifier compares, and the ones it relaxes.
#
# The runner's effective expectation for a case is the value in `config.json`'s
# `TestLocalErrorMap` when the case name is a key there, and the case's own
# built-in `expectedLocalError` otherwise; that is what `-loose-errors` cannot
# relax, and it is what this file audits. A pin is kept only where a document
# in this step's `workdir/docs/specs/` states that alert for the situation the
# case drives (or where the string is the runner's own, which no candidate can
# choose). Where the alert is one implementation's pick from a menu the
# specifications leave open, the pin has been relaxed to the empty string: the
# case still has to fail, but not with a particular alert. Relaxed names are
# listed at the bottom with their reason.

The case drives exactly that configuration -- the shim is started with `-require-any-client-certificate` and the runner's client offers no certificate.

* `TrailingMessageData-CertificateRequest-TLS`, `TrailingMessageData-CertificateStatus-TLS`, `TrailingMessageData-CertificateVerify-TLS`, `TrailingMessageData-ClientCertificate-TLS`, `TrailingMessageData-ClientHello-TLS`, `TrailingMessageData-ClientKeyExchange-TLS`, `TrailingMessageData-NewSessionTicket-TLS`, `TrailingMessageData-ServerCertificate-TLS`, `TrailingMessageData-ServerHello-TLS`, `TrailingMessageData-ServerHelloDone-TLS`, `TrailingMessageData-ServerKeyExchange-TLS`, `TrailingMessageData-TLS13-CertificateRequest-TLS`, `TrailingMessageData-TLS13-ClientCertificate-TLS`, `TrailingMessageData-TLS13-ClientCertificateVerify-TLS`, `TrailingMessageData-TLS13-ClientHello-TLS`, `TrailingMessageData-TLS13-EncryptedExtensions-TLS`, `TrailingMessageData-TLS13-ServerCertificate-TLS`, `TrailingMessageData-TLS13-ServerCertificateVerify-TLS`

* `Client-VerifyDefault-RSA_PKCS1_SHA256-TLS13`, `Client-VerifyDefault-RSA_PKCS1_SHA384-TLS13`, `Client-VerifyDefault-RSA_PKCS1_SHA512-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA256-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA384-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA512-TLS13`
    pinned: any fatal alert (the compared string is `remote error`, with no description)
    citation: the case drives the runner to sign a TLS 1.3 CertificateVerify with rsa_pkcs1_sha256/384/512, which RFC 8446 s4.2.3 says 'refer solely to signatures which appear in certificates ... and are not defined for use in signed TLS handshake messages', and s4.4.3 requires RSA handshake signatures to use RSASSA-PSS. The peer's message is syntactically correct but semantically invalid, which s6 sends to illegal_parameter, so the handshake must be terminated with an alert -- and what this pin compares is only the presence of a fatal alert, not its description. The two SHA-1 siblings at TLS 1.2 (`Client-VerifyDefault-RSA_PKCS1_SHA1-TLS12`, `Server-VerifyDefault-RSA_PKCS1_SHA1-TLS12`) are not scored here; `config.json` pins them to the runner's own `tls: no common signature algorithms`, a string its half produces.

* `Client-Sign-RSA_PKCS1_SHA256-TLS13`, `Client-Sign-RSA_PKCS1_SHA384-TLS13`, `Client-Sign-RSA_PKCS1_SHA512-TLS13`, `Server-Sign-RSA_PKCS1_SHA256-TLS13`, `Server-Sign-RSA_PKCS1_SHA384-TLS13`, `Server-Sign-RSA_PKCS1_SHA512-TLS13`
    pinned: handshake_failure
    citation: the case offers only PKCS1 algorithms in a TLS 1.3 CertificateRequest while the shim holds the certificate and key it must answer with. RFC 8446 s4.2.3 says those values 'refer solely to signatures which appear in certificates ... and are not defined for use in signed TLS handshake messages' and s4.4.3 requires RSA handshake signatures to use RSASSA-PSS, so no signature the candidate can produce is acceptable and the handshake cannot proceed; s6.2 names handshake_failure for exactly that -- 'the sender was unable to negotiate an acceptable set of security parameters given the options available'. Measured on this step's 0.19.0 Oracle: the shim aborts with the alert the pin demands, and its sibling `-TLS12` cases (where PKCS1 is usable) pass without it. A client that ignores the rule and signs with RSA-PKCS1 in TLS 1.3 anyway does not pass the case either -- the runner's own server refuses that signature ('unsupported signature algorithm 0401'), so the failure it reports is not the shim's own alert.

## Pins relaxed (the case must still fail; the alert is not compared)

* `DuplicateExtensionClient-TLS12`, `DuplicateExtensionServer-TLS12`, `DuplicateExtensionClient-TLS13`, `DuplicateExtensionServer-TLS13`
    reason: no document in `workdir/docs/specs/` names an alert for a repeated extension. RFC 8446 s4.2 (and RFC 5246 s7.4.1.4 for the TLS 1.2 half) state the prohibition only -- 'There MUST NOT be more than one extension of the same type in a given extension block' -- and the generic rule in RFC 8446 s6 divides the two readings a parser can take: a message that cannot be parsed according to the syntax draws decode_error, one that is syntactically correct but semantically invalid draws illegal_parameter. Which side a duplicate falls on is a judgement, and implementations sit on both: the built-in pin is decode_error (which is also what 0.19.0 sends for a ClientHello or ServerHello duplicate), while the HelloRetryRequest duplicates higher in the kept list are pinned illegal_parameter with the s6 reading. The pin is relaxed rather than rewritten to either, so both readings pass; what the case still requires is that the handshake fails.

* `GarbageCertificate-Client-TLS12`, `GarbageCertificate-Client-TLS13`
    reason: the built-in pin is decode_error, which no shipped document names for a certificate that cannot be parsed. RFC 5246 s7.2.2 and RFC 8446 s6.2 name the other alert for the situation -- bad_certificate, for 'A certificate was corrupt' -- and that is the alert the `GarbageCertificate-*` cases the later steps score are pinned to (steps 04, 08 and 10 pin all four; step 13 pins the two server-side ones). This release answers a certificate whose DER does not parse with a decode error (webpki's BadDER, turned into AlertDescription::DecodeError by the client's certificate-error path), so the pin cannot be rewritten to the spec-named description without failing the release the case lists were measured from. Relaxed: the handshake must still fail, and either description passes.

* `ClientAuth-NoFallback-ECDSA`
    reason: same situation as ClientAuth-NoFallback-RSA.

* `ClientAuth-NoFallback-RSA`
    reason: no shipped document names an alert for the TLS 1.2 CertificateRequest that omits signature_algorithms which this case drives.

* `ClientAuth-NoFallback-TLS13`
    reason: same situation as ClientAuth-NoFallback-RSA.

* `Resume-Server-ExtraIdentityNoBinder`, `Resume-Server-ExtraIdentityNoBinder-SecondBinder`
    reason: same silence as Resume-Server-ExtraPSKBinder: no alert is named for a count mismatch.

* `Resume-Server-ExtraPSKBinder`, `Resume-Server-ExtraPSKBinder-SecondBinder`
    reason: RFC 8446 s4.2.11 describes the identities/binders lists but names no alert for a count mismatch.

* `Resume-Server-NoPSKBinder`, `Resume-Server-NoPSKBinder-SecondBinder`
    reason: RFC 8446 s4.2.11 says only that a binder which is not present or does not validate makes the server abort; it names no alert for the missing-binder case.

* `SendBogusAlertType`
    reason: RFC 8446 s6 says unknown alerts are fatal but names no alert to answer one with.

* `TLS13-HRR-InvalidCompressionMethod`
    reason: s4.1.3 gives the client no alert for a ServerHello or HelloRetryRequest whose legacy_compression_method is not 0, and the server-side rule (s4.1.2) names illegal_parameter, not the decode_error this case pins.
