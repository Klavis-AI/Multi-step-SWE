# Documentation. No code reads this file.
#
# The alert pins this verifier compares, and the ones it relaxes.
#
# The runner's effective expectation for a case is the value in `config.json`'s
# `TestLocalErrorMap` when the case name is a key there, and the case's own
# built-in `expectedLocalError` otherwise; that is what `-loose-errors` cannot
# relax, and it is what this file audits. A pin is kept only where a document
# in this step's `workdir/docs/specs/` states that alert for the situation the
# case drives (or where the string is the runner's own, which no candidate can
# choose). Where the alert is one implementation's pick from a menu the
# specifications leave open, the pin has been relaxed to the empty string: the
# case still has to fail, but not with a particular alert. Relaxed names are
# listed at the bottom with their reason.

    citation: RFC 8446 s4.1.2: `legacy_session_id` is `opaque<0..32>`; a longer value is a field outside the specified range, which s6.2's decode_error names ('some field was out of the specified range or the length of the message was incorrect').

* `Downgrade-TLS12-Client`
    pinned: illegal_parameter

* `MinimumVersion-Client-TLS13-TLS12-TLS`, `MinimumVersion-Client2-TLS13-TLS12-TLS`, `MinimumVersion-Server-TLS13-TLS12-TLS`, `MinimumVersion-Server2-TLS13-TLS12-TLS`
    pinned: protocol_version
    citation: RFC 8446 Appendix D.1: 'If the version chosen by the server is not supported by the client (or is not acceptable), the client MUST abort the handshake with a "protocol_version" alert'; D.2 gives the server-side half for a ClientHello below everything the server supports; s6.2 defines the alert as 'The protocol version the peer has attempted to negotiate is recognized but not supported'. These are the four of the scored `MinimumVersion-*` cases whose runner maximum is below the shim's minimum, which is the branch that carries an expectation; the others expect the handshake to succeed and carry the empty string.

* `RequireAnyClientCertificate-TLS13`
    pinned: certificate_required
    citation: RFC 8446 s4.4.2.4: a server for which a client certificate is required may 'abort the handshake with a "certificate_required" alert' when the client sends none; s6.2 defines the alert as 'Sent by servers when a client certificate is desired but none was provided by the client'. The case drives exactly that configuration -- the shim is started with `-require-any-client-certificate` and the runner's client offers no certificate.

* `ExpectOmitExtensions`, `NoFallbackSCSV`, `TLS13-TestBadTicketAge-Client`, `NoClientCertificate-TLS12`, `NoClientCertificate-TLS13`, `Downgrade-TLS12-Server`
    pinned: runner-side message
    citation: The pinned string is an error the runner's own half of the connection generates from wire behaviour, not an alert the candidate picks, so no choice is left open. The two `NoClientCertificate-*` entries are the runner's server error in handshake_server.go, reached when the candidate's client -- configured with no certificate -- sends none; `Downgrade-TLS12-Server` is the runner's client error in handshake_client.go, reached when the candidate's server sets the RFC 8446 s4.1.3 downgrade sentinel. In each the candidate's obligation is the wire behaviour the case configures, not the wording of the string.

* `ALPNClient-RejectUnknown-TLS-TLS12`, `ALPNClient-RejectUnknown-TLS-TLS13`
    pinned: illegal_parameter
    citation: RFC 8446 s6.2 illegal_parameter: 'A field in the handshake was incorrect or inconsistent with other fields. This alert is used for errors which conform to the formal protocol syntax but are otherwise incorrect'. The server's ALPN selection is a field inconsistent with the list the client offered, and no_application_protocol is defined in s6.2 for servers only, so it is not the client's answer. Same reading as the `ALPNClient-RejectUnknown-TLS12`/`-TLS13` entry at step 01; this runner spells the cases with a `-TLS-` infix.

* `ALPNServer-Reject-TLS-TLS12`, `ALPNServer-Reject-TLS-TLS13`
    pinned: no_application_protocol
    citation: RFC 7301 s3.2: 'In the event that the server supports no protocols that the client advertises, then the server SHALL respond with a fatal "no_application_protocol" alert.' The case drives exactly that: the shim's server is configured with an ALPN list disjoint from the runner client's.

* `UnsolicitedServerNameAck-TLS-TLS12`, `UnsolicitedServerNameAck-TLS-TLS13`

* `ServerNameExtensionClientMismatch-TLS-TLS12`, `ServerNameExtensionClientMismatch-TLS-TLS13`, `ServerNameExtensionClientMissing-TLS-TLS12`, `ServerNameExtensionClientMissing-TLS-TLS13`

* `TrailingMessageData-CertificateRequest-TLS`, `TrailingMessageData-CertificateStatus-TLS`, `TrailingMessageData-CertificateVerify-TLS`, `TrailingMessageData-ClientCertificate-TLS`, `TrailingMessageData-ClientHello-TLS`, `TrailingMessageData-ClientKeyExchange-TLS`, `TrailingMessageData-NewSessionTicket-TLS`, `TrailingMessageData-ServerCertificate-TLS`, `TrailingMessageData-ServerHello-TLS`, `TrailingMessageData-ServerHelloDone-TLS`, `TrailingMessageData-ServerKeyExchange-TLS`, `TrailingMessageData-TLS13-CertificateRequest-TLS`, `TrailingMessageData-TLS13-ClientCertificate-TLS`, `TrailingMessageData-TLS13-ClientCertificateVerify-TLS`, `TrailingMessageData-TLS13-ClientHello-TLS`, `TrailingMessageData-TLS13-EncryptedExtensions-TLS`, `TrailingMessageData-TLS13-EndOfEarlyData-TLS`, `TrailingMessageData-TLS13-ServerCertificate-TLS`, `TrailingMessageData-TLS13-ServerCertificateVerify-TLS`
    pinned: decode_error
    citation: the case appends a byte to the body of one handshake message and fixes the header length, so the message on the wire declares a body one byte longer than its syntax consumes. RFC 8446 s6's note sends 'a message which cannot be parsed according to the syntax (e.g. have a length extending beyond the message boundary or contain an out-of-range length)' to decode_error, and s6.2 defines decode_error as 'some field was out of the specified range or the length of the message was incorrect'; RFC 5246 s7.2.2 gives the TLS 1.2 half the same definition. * `UnexpectedClientEncryptedExtensions-New-TLS-TLS13`, `UnexpectedClientEncryptedExtensions-Old-TLS-TLS13`
    pinned: unexpected_message
    citation: the runner's client sends an EncryptedExtensions message to the shim's server -- a message only a server may send -- and RFC 8446 s6.2 defines unexpected_message as 'An inappropriate message (e.g., the wrong handshake message, premature Application Data, etc.) was received'. * `Client-Verify-RSA_PKCS1_SHA256-TLS13`, `Client-Verify-RSA_PKCS1_SHA384-TLS13`, `Client-Verify-RSA_PKCS1_SHA512-TLS13`, `Client-VerifyDefault-RSA_PKCS1_SHA256-TLS13`, `Client-VerifyDefault-RSA_PKCS1_SHA384-TLS13`, `Client-VerifyDefault-RSA_PKCS1_SHA512-TLS13`, `Server-Verify-RSA_PKCS1_SHA256-TLS13`, `Server-Verify-RSA_PKCS1_SHA384-TLS13`, `Server-Verify-RSA_PKCS1_SHA512-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA256-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA384-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA512-TLS13`
    pinned: any fatal alert (the compared string is `remote error`, with no description)
    citation: the case drives the runner to sign a TLS 1.3 CertificateVerify with rsa_pkcs1_sha256/384/512, which RFC 8446 s4.2.3 says 'refer solely to signatures which appear in certificates ... and are not defined for use in signed TLS handshake messages', and s4.4.3 requires RSA handshake signatures to use RSASSA-PSS. The peer's message is syntactically correct but semantically invalid, which s6 sends to illegal_parameter, so the handshake must be terminated with an alert -- and what this pin compares is only the presence of a fatal alert, not its description. The two SHA-1 siblings at TLS 1.2 (`Client-VerifyDefault-RSA_PKCS1_SHA1-TLS12`, `Server-VerifyDefault-RSA_PKCS1_SHA1-TLS12`) are not scored at this step; `config.json` pins them to the runner's own `tls: no common signature algorithms`, a string its half produces.

* `Client-Sign-RSA_PKCS1_SHA256-TLS13`, `Client-Sign-RSA_PKCS1_SHA384-TLS13`, `Client-Sign-RSA_PKCS1_SHA512-TLS13`, `Server-Sign-RSA_PKCS1_SHA256-TLS13`, `Server-Sign-RSA_PKCS1_SHA384-TLS13`, `Server-Sign-RSA_PKCS1_SHA512-TLS13`
    pinned: handshake_failure
    citation: the case offers only PKCS1 algorithms in a TLS 1.3 CertificateRequest while the shim holds the certificate and key it must answer with. RFC 8446 s4.2.3 says those values 'refer solely to signatures which appear in certificates ... and are not defined for use in signed TLS handshake messages' and s4.4.3 requires RSA handshake signatures to use RSASSA-PSS, so no signature the candidate can produce is acceptable and the handshake cannot proceed; s6.2 names handshake_failure for exactly that -- 'the sender was unable to negotiate an acceptable set of security parameters given the options available'. Measured on this step's 0.23.0 Oracle: the shim aborts with the alert the pin demands. A client that ignores the rule and signs with RSA-PKCS1 in TLS 1.3 anyway does not pass the case either -- the runner's own server refuses that signature ('unsupported signature algorithm 0401'), so the failure it reports is not the shim's own alert.

## Pins relaxed (the case must still fail; the alert is not compared)

* `ClientAuth-NoFallback-ECDSA`
    reason: same situation as ClientAuth-NoFallback-RSA.

* `ClientAuth-NoFallback-RSA`
    reason: no shipped document names an alert for the TLS 1.2 CertificateRequest that omits signature_algorithms which this case drives.

* `ClientAuth-NoFallback-TLS13`
    reason: same situation as ClientAuth-NoFallback-RSA.

* `EarlyData-SkipEndOfEarlyData-TLS13`
    reason: RFC 8446 names no alert for a client that omits EndOfEarlyData; bad_record_mac is the consequence BoringSSL observes, while detecting the missing message and aborting with unexpected_message is equally conforming.

* `Resume-Server-ExtraIdentityNoBinder`, `Resume-Server-ExtraIdentityNoBinder-SecondBinder`
    reason: same silence as Resume-Server-ExtraPSKBinder: no alert is named for a count mismatch.

* `Resume-Server-ExtraPSKBinder`, `Resume-Server-ExtraPSKBinder-SecondBinder`
    reason: RFC 8446 s4.2.11 describes the identities/binders lists but names no alert for a count mismatch.

* `Resume-Server-NoPSKBinder`, `Resume-Server-NoPSKBinder-SecondBinder`
    reason: RFC 8446 s4.2.11 says only that a binder which is not present or does not validate makes the server abort; it names no alert for the missing-binder case.

* `SendBogusAlertType`
    reason: RFC 8446 s6 says unknown alerts are fatal but names no alert to answer one with.

* `SkipEarlyData-OmitEarlyDataExtension-HelloRetryRequest-TLS13`
    reason: no shipped document names an alert for early data arriving when the early_data extension was not offered.

* `TLS13-HRR-InvalidCompressionMethod`
    reason: s4.1.3 gives the client no alert for a ServerHello or HelloRetryRequest whose legacy_compression_method is not 0, and the server-side rule (s4.1.2) names illegal_parameter, not the decode_error this case pins.

* `TLS13-SendNoKEMModesWithPSK-Server`
    reason: RFC 8446 s4.2.9 says only that servers MUST abort when pre_shared_key arrives without psk_key_exchange_modes; the case drives the present-but-empty form, and the package's own probe grades that situation on the alert level alone.

* `DuplicateExtensionClient-TLS-TLS12`, `DuplicateExtensionServer-TLS-TLS12`, `DuplicateExtensionClient-TLS-TLS13`, `DuplicateExtensionServer-TLS-TLS13`
    reason: the same rule and the same silence as the `DuplicateExtension*-TLS1{2,3}` names relaxed at step 01. RFC 8446 s4.2 states the prohibition only -- 'There MUST NOT be more than one extension of the same type in a given extension block' -- and names no alert for it (RFC 5246 s7.4.1.4 likewise for the TLS 1.2 half); s6 leaves both readings open, decode_error for a message that cannot be parsed according to the syntax and illegal_parameter for one that is syntactically correct but semantically invalid, and this runner's built-in for the spelling is decode_error. Relaxed rather than rewritten to either: the handshake must still fail, and both readings pass.
