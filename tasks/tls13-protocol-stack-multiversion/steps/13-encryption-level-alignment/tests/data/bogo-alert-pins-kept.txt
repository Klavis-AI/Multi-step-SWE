# Documentation. No code reads this file.
#
# The alert pins this verifier compares, and the ones it relaxes.
#
# The runner's effective expectation for a case is the value in `config.json`'s
# `TestLocalErrorMap` when the case name is a key there, and the case's own
# built-in `expectedLocalError` otherwise; that is what `-loose-errors` cannot
# relax, and it is what this file audits. A pin is kept only where a document
# in this step's `workdir/docs/specs/` states that alert for the situation the
# case drives (or where the string is the runner's own, which no candidate can
# choose). Where the alert is one implementation's pick from a menu the
# specifications leave open, the pin has been relaxed to the empty string: the
# case still has to fail, but not with a particular alert. Relaxed names are
# listed at the bottom with their reason.

## Pins still compared

* `EarlyData-Server-BadFinished-TLS13`, `Resume-Server-BinderWrongLength`, `Resume-Server-BinderWrongLength-SecondBinder`, `Resume-Server-InvalidPSKBinder`, `Resume-Server-InvalidPSKBinder-SecondBinder`
    pinned: decrypt_error
    citation: RFC 8446 s6.2 decrypt_error: 'a handshake (not record layer) cryptographic operation failed, including being unable to correctly verify a signature or validate a Finished message or a PSK binder'.

* `Resume-Server-PSKBinderFirstExtension`, `Resume-Server-PSKBinderFirstExtension-SecondBinder`
    pinned: illegal_parameter
    citation: RFC 8446 s4.2.11: 'The pre_shared_key extension MUST be the last extension in the ClientHello ... Servers MUST check that it is the last extension and otherwise fail the handshake with an illegal_parameter alert'.

* `PartialClientFinishedWithClientHello-TLS12-Resume`
    pinned: unexpected_message
    citation: RFC 8446 s5.1: 'Implementations MUST verify that all messages immediately preceding a key change align with a record boundary; if not, then they MUST terminate the connection with an unexpected_message alert'.

* `EarlyData-UnexpectedHandshake-Server-TLS13`, `ServerSkipCertificateVerify`, `ServerSkipCertificateVerify-TLS13`
    pinned: unexpected_message
    citation: RFC 8446 s6.2 unexpected_message: 'An inappropriate message (e.g., the wrong handshake message, premature Application Data, etc.) was received'.

* `GarbageCertificate-Server-TLS12`, `GarbageCertificate-Server-TLS13`
    pinned: bad_certificate
    citation: RFC 5246 s7.2.2 / RFC 8446 s6.2: bad_certificate -- 'A certificate was corrupt, contained signatures that did not verify correctly, etc.' (access_denied is defined for a VALID certificate refused by policy, which a garbage certificate is not).

* `TrailingMessageData-CertificateVerify-TLS`, `TrailingMessageData-ClientCertificate-TLS`, `TrailingMessageData-ClientKeyExchange-TLS`, `TrailingMessageData-TLS13-ClientCertificate-TLS`, `TrailingMessageData-TLS13-ClientCertificateVerify-TLS`, `TrailingMessageData-TLS13-EndOfEarlyData-TLS`
    pinned: decode_error
    citation: the case appends a byte to the body of one handshake message and fixes the header length, so the message on the wire declares a body one byte longer than its syntax consumes. RFC 8446 s6's note sends 'a message which cannot be parsed according to the syntax (e.g. have a length extending beyond the message boundary or contain an out-of-range length)' to decode_error, and s6.2 defines decode_error as 'some field was out of the specified range or the length of the message was incorrect'; RFC 5246 s7.2.2 gives the TLS 1.2 half the same definition. This is not the `TrailingDataWithFinished-*` situation: there the extra byte follows a complete Finished on the wire, where no handshake message may follow; here it is inside the body of the message being parsed.

* `TrailingMessageData-ClientFinished-TLS`, `TrailingMessageData-TLS13-ClientFinished-TLS`
    pinned: decrypt_error
    citation: the extra byte makes the Finished message's verify_data one byte longer than the transcript digest, so the receiver's Finished check fails -- RFC 8446 s6.2 decrypt_error: 'a handshake (not record layer) cryptographic operation failed, including being unable to correctly verify a signature or validate a Finished message or a PSK binder'; RFC 5246 s7.2.2 gives the TLS 1.2 half 'unable to ... validate a finished message'. At this step only the client halves of the family are scored; the server halves carry the same expectation and are recorded at steps 01, 08 and 10 (`TrailingMessageData-ServerFinished-TLS` among them).

* `WrongMessageType-CertificateVerify-TLS`, `WrongMessageType-ClientCertificate-TLS`, `WrongMessageType-ClientFinished-TLS`, `WrongMessageType-ClientKeyExchange-TLS`, `WrongMessageType-TLS13-ClientCertificate-TLS`, `WrongMessageType-TLS13-ClientCertificateVerify-TLS`, `WrongMessageType-TLS13-ClientFinished-TLS`, `WrongMessageType-TLS13-EndOfEarlyData-TLS`
    pinned: unexpected_message
    citation: the case rewrites the type byte of the message the runner sends, so the receiver reads a message that cannot legitimately appear at that point in the handshake. RFC 8446 s6.2 unexpected_message: 'An inappropriate message (e.g., the wrong handshake message, premature Application Data, etc.) was received'; RFC 5246 s7.2.2 defines the TLS 1.2 half as 'unexpected_message: An inappropriate message was received. This alert is always fatal'.

* `UnexpectedClientEncryptedExtensions-New-TLS-TLS13`, `UnexpectedClientEncryptedExtensions-Old-TLS-TLS13`
    pinned: unexpected_message
    citation: the runner's client sends an EncryptedExtensions message to the shim's server -- a message only a server may send -- and RFC 8446 s6.2 defines unexpected_message as 'An inappropriate message (e.g., the wrong handshake message, premature Application Data, etc.) was received'.

* `TrailingDataWithFinished-Server-TLS12`, `TrailingDataWithFinished-Server-TLS13`, `TrailingDataWithFinished-Resume-Server-TLS12`, `TrailingDataWithFinished-Resume-Server-TLS13`
    pinned: unexpected_message
    citation: RFC 8446 s6.2 unexpected_message: 'An inappropriate message (e.g., the wrong handshake message, premature Application Data, etc.) was received'; RFC 5246 s7.2.2 defines the TLS 1.2 half as 'unexpected_message: An inappropriate message was received. This alert is always fatal'. The case drives the runner to put handshake data after its own Finished, where no handshake message may follow, so the alert the specifications name for it is unexpected_message. Same rule as the client-half entries recorded at steps 01, 08 and 10; only these two server halves and their resume forms are scored here.

* `RejectEmptyOCSPResponse-TLS-TLS12`, `RejectEmptyOCSPResponse-TLS-TLS13`
    pinned: decode_error
    citation: the runner's server staples a zero-length OCSP response. RFC 6066 s8 declares the field `opaque OCSPResponse<1..2^24-1>`, so zero bytes is a length outside the specified range -- an error the two generic alerts cover: RFC 8446 s6's note sends 'a message which cannot be parsed according to the syntax (e.g. have a length extending beyond the message boundary or contain an out-of-range length)' to decode_error, and s6.2's decode_error is 'some field was out of the specified range or the length of the message was incorrect' (RFC 5246 s7.2.2 the same for the TLS 1.2 half). In TLS 1.3 the same bound reaches the case through RFC 8446 s4.4.2.1, which requires the "status_request" body to be RFC 6066's CertificateStatus structure. s8's bad_certificate_status_response governs the staple-present callback cases recorded at step 12 -- a response that was received and found unsatisfactory; a zero-length one does not parse at all.

* `RequireAnyClientCertificate-TLS13`
    pinned: certificate_required
    citation: RFC 8446 s4.4.2.4: a server for which a client certificate is required may 'abort the handshake with a "certificate_required" alert' when the client sends none; s6.2 defines the alert as 'Sent by servers when a client certificate is desired but none was provided by the client'. The case drives exactly that configuration -- the shim is started with `-require-any-client-certificate` and the runner's client offers no certificate. Same case and same rule as the entry at steps 01, 08 and 10.

* `CurveTest-Invalid-Compressed-Server-P-256-TLS12`, `CurveTest-Invalid-Compressed-Server-P-384-TLS12`, `CurveTest-Invalid-LowOrderX25519Point-Server-X25519-TLS12`, `CurveTest-Invalid-NotOnCurve-Server-P-256-TLS12`, `CurveTest-Invalid-NotOnCurve-Server-P-384-TLS12`, `CurveTest-Invalid-PadKeyShare-Server-P-256-TLS12`, `CurveTest-Invalid-PadKeyShare-Server-P-384-TLS12`, `CurveTest-Invalid-PadKeyShare-Server-X25519-TLS12`, `CurveTest-Invalid-TruncateKeyShare-Server-P-256-TLS12`, `CurveTest-Invalid-TruncateKeyShare-Server-P-384-TLS12`, `CurveTest-Invalid-TruncateKeyShare-Server-X25519-TLS12`
    pinned: illegal_parameter
    citation: the case hands the candidate's server a TLS 1.2 ECDHE key share that is off the curve, low-order, compressed, truncated by a byte, or padded by one -- the message parses (the length fields are consistent with the bytes delivered) and the share is not a point the group can use. RFC 8446 s6 sends a message that is 'syntactically correct but semantically invalid (e.g., a DHE share of p - 1, or an invalid enum)' to illegal_parameter, and RFC 5246 s7.2.2 defines the alert for the TLS 1.2 half as 'A field in the handshake was out of range or inconsistent with other fields'; RFC 8446 s4.2.8.2 requires peers to validate each other's public value (the TLS 1.2 counterpart is [RFC4492] s5.11, not shipped). The same family at step 11 is recorded there in full. The TLS 1.3 server halves of the family are not scored at this step.

* `Server-Verify-RSA_PKCS1_SHA256-TLS13`, `Server-Verify-RSA_PKCS1_SHA384-TLS13`, `Server-Verify-RSA_PKCS1_SHA512-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA256-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA384-TLS13`, `Server-VerifyDefault-RSA_PKCS1_SHA512-TLS13`
    pinned: illegal_parameter
    citation: the case drives the runner to sign a TLS 1.3 CertificateVerify with rsa_pkcs1_sha256/384/512, which RFC 8446 s4.2.3 says 'refer solely to signatures which appear in certificates ... and are not defined for use in signed TLS handshake messages', and s4.4.3 requires RSA handshake signatures to use RSASSA-PSS. The peer's message is syntactically correct but semantically invalid, which s6 sends to illegal_parameter. Same rule as the verify entries at steps 08 and 10.

## Pins relaxed (the case must still fail; the alert is not compared)

* `EarlyData-SkipEndOfEarlyData-TLS13`
    reason: RFC 8446 names no alert for a client that omits EndOfEarlyData; bad_record_mac is the consequence BoringSSL observes, while detecting the missing message and aborting with unexpected_message is equally conforming.

* `Resume-Server-ExtraIdentityNoBinder`, `Resume-Server-ExtraIdentityNoBinder-SecondBinder`
    reason: same silence as Resume-Server-ExtraPSKBinder: no alert is named for a count mismatch.

* `Resume-Server-ExtraPSKBinder`, `Resume-Server-ExtraPSKBinder-SecondBinder`
    reason: RFC 8446 s4.2.11 describes the identities/binders lists but names no alert for a count mismatch.

* `Resume-Server-NoPSKBinder`, `Resume-Server-NoPSKBinder-SecondBinder`
    reason: RFC 8446 s4.2.11 says only that a binder which is not present or does not validate makes the server abort; it names no alert for the missing-binder case.

* `Resume-Server-OmitAllPSKsOnSecondClientHello`
    reason: no shipped document names an alert for a second ClientHello that drops every PSK.

* `TLS13-SendNoKEMModesWithPSK-Server`
    reason: RFC 8446 s4.2.9 says only that servers MUST abort when pre_shared_key arrives without psk_key_exchange_modes; the case drives the present-but-empty form, and the package's own probe grades that situation on the alert level alone.
