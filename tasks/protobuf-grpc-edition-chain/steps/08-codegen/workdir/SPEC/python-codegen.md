# `--python_out`: the generated `_pb2.py` layout

This is the output format `protoc --python_out` produces, stated precisely
enough to reproduce byte for byte. Every rule here is observable in protoc's
output; several of them fit a single example in more than one way, and those are
called out.

Throughout, `NAME` is the source file path as it appears in
`FileDescriptorProto.name` (e.g. `sub/thing.proto`), and `STEM` is that path
with `.proto` removed.

## 1. File name

The response names one file per file-to-generate, at `STEM + "_pb2.py"`. The
directory part is kept: `sub/thing.proto` generates `sub/thing_pb2.py`.

## 2. Header

```
# -*- coding: utf-8 -*-
# Generated by the protocol buffer compiler.  DO NOT EDIT!
# NO CHECKED-IN PROTOBUF GENCODE
# source: NAME
# Protobuf Python Version: 6.32.1
"""Generated protocol buffer code."""
from google.protobuf import descriptor as _descriptor
from google.protobuf import descriptor_pool as _descriptor_pool
from google.protobuf import runtime_version as _runtime_version
from google.protobuf import symbol_database as _symbol_database
from google.protobuf.internal import builder as _builder
_runtime_version.ValidateProtobufRuntimeVersion(
    _runtime_version.Domain.PUBLIC,
    6,
    32,
    1,
    '',
    'NAME'
)
# @@protoc_insertion_point(imports)
```

Note two separate versions are in play: the four-part `6, 32, 1, ''` above is the
**runtime library** version, which is also what `CodeGeneratorRequest.compiler_version`
carries. It is not the `32.1` that `protoc --version` prints.

## 3. Imports and the blank-line template

After the insertion point the layout is a template, not a count:

```
<blank>
_sym_db = _symbol_database.Default()
<blank>
<blank>
<one import line per entry in FileDescriptorProto.dependency, in order>
<blank>
<blank>
DESCRIPTOR = _descriptor_pool.Default().AddSerializedFile(b'...')
<blank>
_globals = globals()
```

With no dependencies the two pairs of blanks meet, giving four consecutive blank
lines. That is a consequence of the template, not a rule of its own.

An import line is built from the dependency's path `DEP` (with `.proto`
removed):

- alias = `DEP` with every `_` doubled and every `/` replaced by `_dot_`, then
  `__pb2` appended.
- if `DEP` has no directory: `import DEP_pb2 as ALIAS`
- otherwise, with `DIR` the directory part (slashes turned into dots) and `BASE`
  the final component: `from DIR import BASE_pb2 as ALIAS`

So `t_dep.proto` gives `import t_dep_pb2 as t__dep__pb2`, and
`sub/t_sub.proto` gives `from sub import t_sub_pb2 as sub_dot_t__sub__pb2`.

## 4. The serialized blob

`AddSerializedFile` carries the file's `FileDescriptorProto` **re-serialised with
`json_name` suppressed on every field**, including fields of nested messages and
both file-level and nested `extension` entries. Everything else is preserved
exactly as the descriptor holds it, in the same field order.

The bytes are written as a Python bytes literal with this escaping:

- `\n`, `\r`, `\t`, `\'`, `\"`, `\\` are written in those forms;
- any other byte in `0x20..0x7E` is written literally, **except** when it is a
  hex digit (`0-9 a-f A-F`) and the byte before it was written as a `\xNN`
  escape — then it too is escaped;
- everything else is written as lowercase `\xNN`.

The exception is why `\x12\x02cg` is written `\x12\x02\x63g`: a literal `c` after
`\x02` would read as a continuation of the hex escape.

## 5. The builder call

```
_builder.BuildMessageAndEnumDescriptors(DESCRIPTOR, _globals)
_builder.BuildTopDescriptorsAndMessages(DESCRIPTOR, 'MODULE_pb2', _globals)
```

`MODULE` is `STEM` with `/` replaced by `.`. A flat file cannot show this: the
generated file name keeps the slash while this argument takes a dot.

## 6. The `_USE_C_DESCRIPTORS` block

```
if not _descriptor._USE_C_DESCRIPTORS:
  <file options line(s)>
  <option lines>
  <offset lines>
# @@protoc_insertion_point(module_scope)
```

Every line inside is indented two spaces.

### Python names

A top-level entity is `_` followed by its proto name upper-cased. A nested one
appends `_` and its own upper-cased name to its parent's Python name, so
`Gen.MEntry` is `_GEN_MENTRY` and `A.B.C` is `_A_B_C`.

### File options

If the file has **no** options:

```
  DESCRIPTOR._loaded_options = None
```

If it **has** options, the line takes a different form — this is a change of
shape, not an added line:

```
  _globals['DESCRIPTOR']._loaded_options = None
  _globals['DESCRIPTOR']._serialized_options = b'...'
```

### Option lines

An entity with options contributes two lines:

```
  _globals['PYNAME']._loaded_options = None
  _globals['PYNAME']._serialized_options = b'...'
```

and a **field** with options contributes:

```
  _globals['PYNAME'].fields_by_name['field']._loaded_options = None
  _globals['PYNAME'].fields_by_name['field']._serialized_options = b'...'
```

`_serialized_options` uses a different escaper from the blob: the same special
forms (`\n \r \t \' \" \\`), printable bytes literally, and everything else as
three-digit **octal** `\ooo`. So byte 0x0A is `\n` while 0x0B is `\013`.

The order is a post-order walk, and it is not wire order:

1. the file's own options;
2. each top-level enum, in declaration order;
3. each top-level message as a block, in declaration order.

A message's block is:

1. each nested message, recursively, as its own block;
2. each nested enum;
3. the message's own fields that have options, in declaration order;
4. **the message itself, last** — after the fields it contains.

A file with only one option-bearing entity is consistent with several simpler
rules; a file with a map (which gives its entry type options), a `[packed=true]`
field and a message-level option distinguishes them.

### Offset lines

Every message, enum and service contributes:

```
  _globals['PYNAME']._serialized_start=N
  _globals['PYNAME']._serialized_end=M
```

`N` is the offset **of the entity's content** within the serialized blob — after
its tag and length bytes — and `M` is `N` plus that content's length.

The listing order differs between the two levels, and they disagree:

- **File level:** every enum first (declaration order), then every message, then
  every service.
- **Within a message:** the message itself, then its nested messages
  recursively, then its nested enums.

So a file declaring message, enum, message lists the enum first; but a message
declaring enum-then-nested-message lists the nested message first. Neither order
alone can be inferred from a file whose declarations happen to match it.
