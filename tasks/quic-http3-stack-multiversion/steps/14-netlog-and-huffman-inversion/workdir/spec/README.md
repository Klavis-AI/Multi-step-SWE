# Specification material — step 14

The full text of every RFC this task touches is in this directory,
byte-identical to the IETF originals (`SHA256SUMS` covers them). It is
here so the milestone can be worked offline and so that every step reads
the same words. This environment has no general network access, so these
documents and what the image already holds are all the reference material
there is.

What is load-bearing *for this step*:

| document | sections | why it matters here |
| --- | --- | --- |
| `rfc9000.txt` | 3.5 (solicited state transitions), 7.3 (authenticating connection IDs), 8.1.2 (address validation using Retry packets), 13.3 (retransmission of information), 14.2 (path maximum transmission unit), 14.3 (datagram packetization layer PMTU discovery), 17.2.5 (Retry packet), 19.5 (STOP_SENDING frames) | 13.3 is the single most load-bearing section for this step, and it is short. It lists, frame family by frame family, what an endpoint does when a packet it sent is declared lost. Most control frames are re-sent as the *current* state rather than the state they carried; connection-close signals are not re-sent at all; and STOP_SENDING has a rule of its own, quoted here because the scored case is a direct transcription of it: the request *is sent until the receiving part of the stream enters either a "Data Recvd" or "Reset Recvd" state*. Read it for the condition, not just the permission -- the sentence forbids something as well as requiring something, and both halves are checked. 3.5 is what that condition means. It is the section that defines why one endpoint asks another to stop sending at all, what states the request is useful in, and what the peer is obliged to do with it. Read it before deciding what "the peer has finished" means: it is a property of the receiving half of the stream at the endpoint that sent the frame, and it is reached by the peer's fin arriving, not by anything the sender does. 19.5 is the wire format underneath, two variable-length integers, and it is the reason a retransmission carries the same stream id and application error code as the original rather than a refreshed value. 8.1.2 and 17.2.5 are the Retry exchange `accept_with_retry` completes. 8.1.2 describes the round trip -- server refuses to commit state, sends a Retry with a token and a new source connection ID, client retries with the token, server validates it -- and 17.2.5 is the packet itself, including the retry integrity tag that makes it unforgeable. Read 8.1.2 for the sentence about the client's subsequent Initial being sent to the Retry's source connection ID, which is why a server that changes that ID later has to say so. 7.3 is why saying so is mandatory rather than polite. It requires the server to echo, in its transport parameters, both the destination connection ID from the client's first Initial and the source connection ID of the Retry, and requires the client to close the connection with a transport parameter error if either does not match what it observed. That requirement, and not any behaviour this crate invents, is what makes a wrong `RetryConnectionIds` a `0x08` close. 14.2 and 14.3 are the vocabulary of `pmtu()`. 14.2 is the path MTU as a property of the path rather than of the endpoint, and the 1200-byte floor that every QUIC path must clear; 14.3 is DPLPMTUD, the search procedure, which is why the answer is a value that was *confirmed* by a probe and its acknowledgement rather than a value that was assumed. Read 14.3 for why the accessor returns an option: while the search is running there genuinely is no discovered PMTU, and the connection works anyway. |
| `rfc9002.txt` | 6 (loss detection), 6.1 (acknowledgment-based detection), 6.2 (probe timeout) | Section 6 is where "the packet was lost" acquires a definition. Nothing on the wire says a packet was lost; an endpoint *declares* it lost, on its own judgement, and Section 6 is the set of rules for that judgement. Read it first, because the STOP_SENDING behaviour this step adds is triggered by a declaration and not by an event. 6.1 is the declaration the scored case relies on. A packet is lost when a later packet has been acknowledged and the gap is wide enough -- the packet reordering threshold, three packets -- or old enough. The packet threshold is the deterministic half of the section: it depends on how many later packets the peer acknowledged, which the case controls exactly, and not on elapsed time, which it does not. That is why the case establishes loss by delivering later packets and withholding one, rather than by waiting. 6.2 is the timer-driven half, and it is here so that it can be recognised and avoided. A probe timeout fires on a clock and sends new data to elicit an acknowledgement; anything that depends on it is a race. Read 6.2 to see what this step's observations are deliberately not built on. |
| `rfc9204.txt` | 4.1.1 (prefixed integers), 4.1.2 (string literals), 7.2 (static Huffman encoding) | 4.1.2 is the reason the Huffman coder exists and the reason it is allowed to refuse. A QPACK string literal is a length-prefixed byte string preceded by a single bit saying whether it is Huffman coded, and *when Huffman encoding is enabled, the Huffman table from Appendix B of RFC 7541 is used*. Two things follow, and both are in the scored case. The table is not this crate's invention, so its outputs are fixed by the specification rather than chosen -- there is exactly one correct encoding of a given input. And the bit exists because coding is optional per string: an encoder is expected to compare the two forms and pick the shorter, which is exactly the decision `huffman_encoding_len` refusing to measure an unprofitable input hands back to its caller. 4.1.1 is the length that precedes the string, a prefixed integer whose prefix shares a byte with the Huffman bit. It is worth reading for one detail: the length on the wire is the length of the *encoded* form, so an encoder has to know how long the encoding will be before it writes it. That is why a size-only entry point is part of the surface rather than an optimisation. 7.2 is the security note on using a static table, and it is the reason the table is static in the first place: a code computed from the data being coded leaks about the data, and a fixed code does not. Read it for why no part of this surface is adaptive, and therefore why the same input coded twice, in two processes, at two times, produces the same bytes. The Huffman table itself is in Appendix B of RFC 7541, which is not in this corpus. It is not needed: every value the scored case checks is stated in the interface document as a table, and an implementation that ports the code from where it already lives in this repository does not need to re-derive it. |
| `rfc9114.txt` | 4.1 (HTTP message framing), 7.2.1 (DATA), 7.2.2 (HEADERS), 7.2.4 (SETTINGS) | This one is read for vocabulary rather than for behaviour. The netlog fixture the scored case parses is a recording of an HTTP/3 session, and the events in it are named after the frames in this section: a headers-sent event, a headers-decoded event, a data-sent event with a payload length, a settings-sent event. A reader that does not know what those are cannot tell a plausible fixture from an implausible one. 4.1 is the shape of a message as a sequence of frames, and it is why the fixture's events appear in the order they do -- the request header section, then the response header section, then body. 7.2.2 is the HEADERS frame, whose payload is a QPACK-encoded field section, which is where this specification meets the previous one: the header lists the netlog carries are the decoded form of exactly the string literals Section 4.1.2 of RFC 9204 describes. 7.2.1 is DATA, and it is why a data event's interesting field is a length rather than a payload. 7.2.4 is SETTINGS, and it is in the fixture as an event the parser is expected to recognise by name and then decline to model -- which is the ordinary case for a netlog consumer and is asserted as such. The priority-update event in the fixture carries an opaque field value and an element type. The frame it records is an HTTP/3 extension defined in RFC 9218 rather than here, and the parser treats its value as the uninterpreted string it is, so nothing about this step requires that document. |

`appendix-a-vectors.json` holds RFC 9001 Appendix A's worked
example decomposed into named byte strings. The grader uses the same
file, so a disagreement with it is a disagreement with the RFC.
