# Specification material — step 15

The full text of every RFC this task touches is in this directory,
byte-identical to the IETF originals (`SHA256SUMS` covers them). It is
here so the milestone can be worked offline and so that every step reads
the same words. This environment has no general network access, so these
documents and what the image already holds are all the reference material
there is.

What is load-bearing *for this step*:

| document | sections | why it matters here |
| --- | --- | --- |
| `rfc9114.txt` | 4.2.1 (field compression), 4.2.2 (header size constraints), 7.2.4 (SETTINGS), 7.2.4.1 (defined SETTINGS parameters) | 7.2.4.1 is where the number this step starts advertising is defined. SETTINGS_MAX_FIELD_SECTION_SIZE is identifier `0x06`, and the section states both halves of what it means: it is the size of the *decoded* field section an endpoint is willing to accept, and the default when the setting is absent is unlimited. Those two sentences are the whole of the change. Until this milestone the setting was absent and the peer was told nothing; now it is present and the peer is told 32768. 4.2.2 is the size the setting measures, and it is worth reading because the number is not the number of bytes on the wire. A field section's size is the sum, over its fields, of the name length plus the value length plus 32 -- an overhead per field that exists so the limit bounds the receiver's memory rather than its input. An implementation that compared the limit against the encoded HEADERS payload would be measuring a different quantity. 4.2.1 is why those two are different quantities: the field section is QPACK compressed, so the encoded form is smaller than what it decodes to, and by an amount the sender chooses. Read it for the direction of the inequality. 7.2.4 is the frame the value travels in, and the two rules that make the scored case's reading of it sound: SETTINGS is sent once, first, on each endpoint's control stream, and a receiver must tolerate identifiers it does not recognise. The second is why the case looks for its identifier in the list rather than insisting the list is exactly one pair long. |
| `rfc9221.txt` | 3 (transport parameter), 4 (datagram frame types), 5 (behavior and usage), 5.3 (flow control) | Section 3 is the negotiation the `InvalidState` answer reports. DATAGRAM support is advertised by a transport parameter, and an endpoint must not send a DATAGRAM frame to a peer that did not send it. So a send on a connection whose peer never advertised the extension is not a failure to queue something -- it is a frame the endpoint is forbidden to write, which is why the answer is a state error rather than a capacity error. Section 4 is the frame, and the reason the length limit is hard. A DATAGRAM frame's payload must fit in a single QUIC packet: the frame is not fragmented and there is no mechanism to reassemble one. That is why a buffer one byte too long is refused outright rather than split, and why the accessor that reports the writable length is the boundary the scored case tests on both sides. Section 5 is the delivery contract that makes an owned-buffer API meaningful at all. DATAGRAMs are unreliable and unordered, they are not retransmitted on loss, and they are not stream data -- the last of which the regression case checks directly by asserting that a received DATAGRAM opens no stream. 5.3 is the sentence that they are not flow controlled, which is why the send queue's bound is the implementation's own and not the peer's. |
| `rfc9000.txt` | 2.2 (sending and receiving data), 2.4 (operations on streams), 3.1 (sending stream states), 3.2 (receiving stream states), 3.4 (bidirectional stream states), 4.1 (data flow control) | 3.2 is the definition `stream_readable_len` has to respect. A receiving stream holds data that arrived, at the offsets it arrived at, and the section is explicit that data can arrive out of order: the receiver buffers it and delivers it to the application in order. So there are two quantities -- what has arrived and what can be read -- and they are equal only when nothing is missing. Read it before deciding what the count counts. 2.2 is the same distinction from the application's side, and it carries the sentence the accessor exists to serve: an endpoint must not deliver stream data out of order. 2.4 is the operations an application is offered on a stream, and it is the section that frames a read as "how much is available" followed by "take it", which is the pair the new accessor completes. 3.1, 3.2 and 3.4 together are `stream_closed`. 3.1 is the sending half's state machine, ending in the states reached after the final frame is sent and acknowledged; 3.2 is the receiving half's, ending after the final offset is known and read; 3.4 composes the two and states plainly that a bidirectional stream is closed only when both halves are. Read 3.4 for the asymmetry a unidirectional stream has: only one half exists, so only one half can be waited for, and waiting for the other would be waiting forever. 4.1 is the reason the scored cases can send what they send. Flow control is a credit the receiver grants per stream and per connection, and a sender that runs out queues rather than fails. The cases stay well inside the limits the verifier configures so that a short write is never mistaken for the behaviour being observed. |
| `rfc9001.txt` | 4.1 (interface to TLS), 4.7 (HelloRetryRequest), 4.8 (TLS errors) | 4.1 is the boundary `set_curves_list` reaches across. QUIC does not implement the handshake; it hands CRYPTO stream bytes to TLS and takes keys back, and the key exchange -- which group, with which share -- is entirely TLS's business. That is why the setter is a pass-through to the TLS library rather than something the transport interprets, and why its error is a TLS error. 4.7 is the first thing that can happen when the two sides' group preferences do not line up, and it is the case the scored group deliberately does not test: if the client supports a group the server wants but did not send a share for, the server asks for one and the handshake continues, one round trip longer. Read it so that "no group in common" is understood as a different situation from "no share in common", and so that the configuration the case uses -- disjoint preference lists, not merely a missing share -- is understood to be the one that cannot be recovered. 4.8 is what happens then. A TLS alert becomes a QUIC connection error in the CRYPTO_ERROR range, and the handshake ends. Read it for the shape of the failure the scored case observes: neither endpoint reaches the established state, and the failure is a connection error rather than a hang. |
