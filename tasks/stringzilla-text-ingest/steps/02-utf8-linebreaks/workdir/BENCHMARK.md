# How to check your work

## Build

```bash
cmake -S /app/stringzilla -B /app/build -DCMAKE_BUILD_TYPE=Release \
      -DSTRINGZILLA_BUILD_TEST=ON -DSTRINGZILLA_BUILD_BENCHMARK=OFF \
      -DSTRINGZILLA_BUILD_SHARED=OFF -DSTRINGZILLA_USE_SANITIZERS=OFF \
      -DCMAKE_C_FLAGS="-mavx2 -mbmi -mbmi2 -maes -mpclmul -msse4.2 -mlzcnt -mpopcnt -Wno-error=maybe-uninitialized -Wno-error=uninitialized" \
      -DCMAKE_CXX_FLAGS="-mavx2 -mbmi -mbmi2 -maes -mpclmul -msse4.2 -mlzcnt -mpopcnt -Wno-error=maybe-uninitialized -Wno-error=uninitialized"
cmake --build /app/build -j"$(nproc)"
```

The two `-Wno-error=` relaxations are part of the exact command line the
verifier compiles with, so keep them in your own build: the project promotes
several warnings to errors, and a local build that is stricter than the build
the verifier uses fails work the verifier would accept.

## Behaviour must not change

The library has to produce exactly the bytes it produced before, for every input
and configuration. All of these are re-run, with fixtures you cannot see, when
your work is checked.

1. **Upstream's own suite** must gain no new failure. The verifier runs the
   project's C++20 test binary —
   `cmake --build /app/build --target stringzilla_test_cpp20 && ctest --test-dir
   /app/build -R stringzilla_test_cpp20` — and compares its failures against the
   same binary's failures in the tree you inherited. Only *new* failures are
   regressions.
2. **The entry points this milestone covers** must produce byte-identical
   output to the versions you inherited. The verifier calls both trees' entry
   points on the same generated inputs and compares the results exactly — an
   approximation, or a fast path that is right "almost always", fails.
3. **The whole ingest pass must not get slower.** The verifier runs the pipeline
   end to end (index, segment, fold, search, hash) and compares it against the
   floor set by the tree with every one of this task's optimizations absent —
   that is, against a tree that has done nothing. More than **25% slower** than
   that floor fails; both sides are timed seven times and compared by their best
   run, so a busy machine cannot fail this on its own.
4. **The capability envelope.** The files this milestone owns — and anything
   their headers pull in — are scanned for AVX-512 constructs and for SHA-NI.
   This host has no AVX-512 at all, and though its CPU lists SHA-NI, the pinned
   command line does not enable it and no reference kernel uses it. Every run
   of your tree under the measurement is single-threaded as well: the
   reference creates no threads, so a kernel that spawns threads or child
   processes cannot gain from them here.

## How your work is timed

Each entry point this milestone covers is timed **individually**, by calling the
implementation the library installs for it — not by timing the whole pipeline.
That means a faster entry point shows up at its full value instead of being
diluted by everything around it, and every entry point in the list below is
timed, so none of your work goes unnoticed. A function left alone is not faster.

This milestone is timed on:

- `sz_utf8_linebreaks`

The tool below reproduces the shape of that measurement, on a *different*
corpus from the measurement one:

```bash
/app/tools/build.sh                      # rebuild it against your headers
/app/tools/measure sz_utf8_linebreaks    # one entry point, microseconds, lower is better
/app/tools/measure                       # no argument: prints a usage line
```

Each number it prints is the median of seven repetitions, and each repetition
uses a freshly generated input, so a result cannot be cached behind the call —
it also prints a checksum of all seven repetitions' outputs, and the verifier
compares that checksum between your tree and the reference: an answer served
from a cache behind the call does not change when its input does, and the
checksum shows it. The measurement takes the median of five such runs,
alternating between your tree and the reference tree on the same pinned cores,
so a busy machine moves both sides. Treat your own numbers as indicative: **the verifier's
measurement is the authoritative one.**

**The workload is generated by the verifier and is not disclosed** — not the
corpus, not its draw, not the shape parameters. It is deterministic, so it is
the same for every candidate. Optimize the family for the general case; a kernel
that only wins on one shape of input does not cover the requirement.
