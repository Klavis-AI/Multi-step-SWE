# Step 6 — O-RAN fronthaul IQ compression

## 1. Implement this milestone

`/app/srsran` is the srsRAN Project 5G RAN at a pinned upstream commit with the
optimized implementation of one or more physical-layer DSP kernels removed, for
**every** architecture. The library is complete and correct: it builds, it
passes its own suite, and it processes every slot correctly through the portable
implementations. It is simply slow in the places whose optimized code is
missing.

**This milestone: make O-RAN fronthaul IQ compression and packing faster, without changing a single output byte.**

It covers two paths of the O-RAN fronthaul serialisation, which share their bit packing: the block-floating-point compressor and decompressor — the per-PRB exponent search, the quantisation that follows from it, and the sub-byte packing that crosses byte boundaries — at the 9-bit and 16-bit widths, and the uncompressed path's 16-bit pack into, and unpack out of, a byte buffer in network order.

The kernel currently has no optimized implementation at all: the portable code
is what the library installs. How you make it faster is your choice —
intrinsics in a new file registered in the component's `CMakeLists.txt`,
intrinsics in the existing translation units, or work on the portable
implementation itself. **You are measured on the implementation the library
installs for its default selector**, so any route that makes what the library
installs faster is acceptable.

Earlier milestones must keep working. This workspace is cumulative: kernels you
optimized in earlier milestones are still here and are still part of this
milestone's baseline, so a regression breaks both the earlier work and this
milestone's baseline.

Only the block-floating-point path's 9-bit and 16-bit widths and the uncompressed path's 16-bit width are in scope. The other widths the interface accepts are not measured at all, on either side of the comparison.

**What success means here.**

1. **The library must behave exactly as it does now.** This is an optimization
   task, not a behaviour-change task: this kernel must produce byte-identical
   output to the tree you started from, for every input and every configuration
   — not merely for the cases you happen to test. An approximation, a fast path
   that is right "almost always", or a reordering that changes rounding is a
   failure, however fast it is.
2. **This kernel must get faster** on the workload named in `/app/BENCHMARK.md`.
   Only this kernel is in scope. Optimizing some other part of the library is
   out of scope for this milestone, and so is effort that does not show up in
   the measurement.

`/app/BENCHMARK.md` gives the exact commands for both — the behaviour checks and
the timing — so you can confirm where you stand before finishing. The same
checks are re-run, with a hidden draw, by the checker.

**The workload is generated by the checker, not chosen by you.** You are told the
family of inputs this kernel is measured on — the bit width and the IQ values — and you are not told the
draw. Optimize this kernel for the general case rather than for one setting; a
kernel that only wins on one configuration does not satisfy this milestone.

The scoped functions, one per line, are:

  - `ofh_bfp9_compress`
  - `ofh_bfp9_decompress`
  - `ofh_bfp16_compress`
  - `ofh_bfp16_decompress`
  - `ofh_none16_compress`
  - `ofh_none16_decompress`

## 3. Meta requirements

- The implementation budget is 7,200 seconds. Check `bash /app/timer.sh`;
  the configured timeout is authoritative and resets for this step.
- Work in the cumulative `/app` workspace. Keep `/app/srsran` as the source
  tree and keep the upstream build system working:
  `cmake -S /app/srsran -B /app/build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
  -DMARCH=x86-64-v3 -DENABLE_WERROR=OFF -DENABLE_MKL=OFF -DENABLE_ARMPL=OFF
  -DENABLE_UHD=OFF -DENABLE_ZEROMQ=OFF -DENABLE_BACKWARD=OFF -DENABLE_PLUGINS=OFF`
- **The library's other kernels must keep working.** A change that makes this
  kernel faster by making another one slower is not a solution, and the
  checker checks for it: it strips this milestone's implementation out of a
  copy of your tree, rebuilds, and re-times every function the harness knows on
  both sides. That check is skipped, and reported as skipped rather than as
  satisfied, when the stripped copy cannot be produced, for instance because the
  implementation was delivered in a file the stripping does not recognise; the
  per-function checks above still cover correctness.
- **Stay inside the machine the reference was written for.** The tree is built with
  `-DMARCH=x86-64-v3`, which is AVX2 and FMA; the target host has no AVX-512.
  Your changes must not add a `-mavx512*` compiler flag — `-march=native` and a
  `#pragma GCC target("avx512...")` reach the same thing by another spelling and
  are checked the same way — and must not use AVX-512 intrinsics or `__m512`
  types. What is checked is every source or CMake file you write, whether or not
  the build compiles it.
  This is a fairness rule, not a technical one: the comparison is against an
  implementation that saturates AVX2, so reaching wider would be measured on a
  capability it never had. (An AVX-512 block behind its own
  `#if defined(__AVX512F__)` guard is dead in this build and gains nothing,
  so it is not held against you — it is also not an optimization.)
- **Single-threaded.** One call runs on one pinned core on both sides of the
  comparison. Do not spawn threads, use a thread pool, or open a parallel
  region: `std::thread`, `std::async`, `<thread>`, `pthread_create`,
  `pthread_join` and any `#pragma omp` directive, parallel or not, are checked
  wherever they appear in a source file you write. A kernel that wins by using
  more cores has not made the kernel faster.
- You do not have network access. **Do not fetch, copy, vendor, or transcribe
  srsRAN's own optimized implementation of this kernel, or any other project's,
  from the internet or a package mirror.** The optimization must be yours. Do
  not inspect `/tests`, later-step directories, or solution material.
- Do not weaken, filter, rename, or disable tests.
- Leave a reproducible handoff in `/app/WORKSPACE_HANDOFF.md`: what you changed,
  the speedup you measured locally, and how to rebuild.
